# ADR-026: 固定空间布局（模式只改语义，不改位置）

## 1. 标题与日期

- **标题**：`interactionMode` 不再驱动区域重排——调用态 / 整理态共享同一套空间布局，模式差异收敛回「点击语义 + 动作显隐」
- **日期**：2026-08-18
- **决策者**：omar（**待审**）；起草：Claude（🤝 共创文档，见 [[CLAUDE#§5.2]]）
- **影响范围**：
  - **代码**：`src/layouts/Dashboard.tsx`（删条件分支）/ `src/layouts/Dashboard.module.css`（cockpit 段并入主布局）/ `src/components/MacroGrid.module.css`（`--macro-strip-cap` 退役）/ `src/App.test.tsx`（两条模式分歧的 region order 测试合一）
  - **文档**：[[03-product-spec]] §4.0.4 UI 共用规则表（模块位置以本决策为准重写）+ §4.0.7（补一句「模式不改布局」反设计）+ §13.3 区域 4/5/6 位置字段 + §13.4 Tab 顺序追认
  - **ADR**：不推翻 [[023-ui-reshape-before-release]]（它决的是「发布前做一次系统性重塑」，未决布局形态）；沿用 [[016-choose-dnd-and-resizable-layout]] 的 Group/Panel 承载新增的纵向分配

## 2. Status

`Accepted`（2026-08-18 起草并由 omar 当日拍板）

> **落地进度**：代码当日实施完毕。`Dashboard.tsx` 条件分支删除（-45 行），`Dashboard.module.css` 的 `.cockpitMain` / `.cockpitRail` / `.modifierTray` / `.macroSlot` 四段移除，`ModifierGrid` 的 `dense` 变体与 `.cardDense` 随底部 tray 一并退役，`--macro-strip-cap` 间接层消失。左列新增纵向 `Group`（`task-2row`），Macro 默认 46% / min `132px`，Scene 默认 54% / min `196px`——**最小值取像素而非百分比**，正是为了不复制旧 wake「38% 无下限」那笔债。`App.test.tsx` 两条模式分歧断言合并为一条 `it.each`，「pending human review」注释删除。335 测试 / eslint / prettier / `pnpm build` 全绿。
>
> **真机验收结论（2026-08-19 走查，1470×956）**：三项全过，已合入 `main`。起草时的推算有两处口径错误，一并订正如下。
>
> **口径订正 1——「640px 基线窗口」不可复现**：主形态窗口**恒等于当前显示器尺寸**（`src-tauri/src/lib.rs:24` `fit_to_active_monitor` 每次唤起重新铺满），`tauri.conf.json` 的 `800×600` 仅为占位。故不存在「640px 基线窗口」这一可测场景，真实下限场景是「最小显示器」。
>
> **口径订正 2——推算高估 chrome 约 48px**：实测结构 chrome 为 panorama 上方 `195.5px`（frame inset 12 + Header 53 + 协议 band 129.5）、`任务层` 标记行 `26.5px`、下方 `41px`（状态栏 28 + hairline + inset 12），即 `taskGroup = 窗口高 − 263`。按此口径，640px 时 taskGroup 为 `377px` 而非起草时推算的 `424px`——余量是 48px 不是 96px。
>
> **挤压阈值（Scene 下限修正后）**：两下限合计 `132 + 1 + 288 = 421px` ⇒ **窗口高 < 684px 才会挤压**（修正前为 592px）。主形态窗口恒等于显示器高度，常见最小显示器 1366×768 仍有 84px 余量。⚠️ 但 `HotkeyBanner` / `UpdaterBanner` 同时出现时各再吃约 33px，阈值升至约 `750px`，与 768px 只差 18px——**若日后再加常驻横幅，需重新核算本阈值**。
>
> **实测项**：
> - **纵向下限**：拖至极限，Macro 停在 `133px`、Scene 停在 `196px`，**两个像素下限均真实生效**——未复制旧 wake「38% 无下限」那笔债 ✅。但 `196px` 的**取值**不达标，已改 `288px` 并复测（separator 停 626，Scene = `288px`，首卡完整 + 次卡露边），见下方裁决表第 1 项
> - **Separator 命中与光标**：库按 `resizeTargetMinimumSize` 默认 `{coarse: 20, fine: 10}` 将 1px 视觉条撑至**鼠标 10px / 触控 20px**，且 hover 态即注入 `ns-resize` ✅
> - **PhaseBar 等宽后活动相位**：可辨 ✅——但量化显示识别几乎全由下划线 `(63,106,214)` 2px + 实底序号章 + `--w-600` 承担
> - **本 ADR 核心主张的直接证据**：切模式前后按像素扫描区域边界，三条竖列（x=20/700/1200）纵向边界**完全相同**，横向列分割恒在 x=979/980。这正是 jsdom 验不了的部分
>
**走查另发现三项缺陷，2026-08-19 已逐项裁决**：

| # | 发现 | 裁决 | 依据 |
|---|---|---|---|
| 1 | Scene `196px` 下压到底时 **0 条话术**，且 `.phrases` 滚动条被 `scrollbar-width: none` 隐藏，无「下面还有」提示 | **修 → `288px`** | **不是新设计决策，是没满足子决策 2 自己写的验收条件**（见该节修正块）。取值经实测：224 结构 + 首卡完整 265 + 次卡露边 288 |
| 2 | Separator 约 9px 视觉死区——命中区由库撑到 10px 且光标已变 `ns-resize`，而 `.separatorRow:hover` 只在压中那 1px 时亮（库仅挂 `data-separator`，无状态属性可供 CSS 挂钩）| **不修，记为已知可接受** | 扩 hover 需绝对定位 `::before`，其透明带会**吞掉 Macro 末行卡片的点击**。光标是主 affordance 且已覆盖同样 10px；用真实点击回归风险换次要视觉确认不划算 |
| 3 | `--brand-dim` 活动底 `(29,36,53)` vs 非活动 `(24,24,27)`，对比度仅 **1.145:1**，远低于 WCAG 1.4.11 非文本 3:1 | **不调色，改为把下划线钉成承重件** | 1.4.11 要求**状态可辨**而非每个线索达标；下划线 + 实底序号章 + `--w-600` 已足。调色阶会改动整个 band 视觉语言，违反 [[025-unified-anchored-editing]]「未新增任何视觉语汇」 |

> **第 3 项裁决的真正价值不在配色，在防拆**：CLAUDE §5.1.1 减法快车道把「删装饰」列为免八步四类之一，而 `.phase.active::after` 那条下划线**外观上就像装饰**——将来任何人走快车道顺手删掉，活动相位当场塌陷且无需评审。已在 `PhaseBar.module.css` 就地标注 **LOAD-BEARING / 禁止按装饰处理 / 改动走八步**。同理 `.separatorRow` 的已知死区也就地留注，防止后人重新"发现"并踩进点击吞噬的坑。

## 3. Context

### 触发事件

外部独立评价（2026-08-17）指出：「模式切换改变的不只是行为，而是整个页面布局……用户无法形成『Macro 永远在这里』的肌肉记忆。汽车从行驶模式切到运动模式，不会把速度表和转速表对调。」

复核代码后，这不是审美分歧——**它是一处未经决策的契约越界**。

### 事实一：dual-layout 从未进过任何决策文档

`Dashboard.tsx:28-36` 的实现注释自陈：

> 「Reshape v2 dual-layout: the interaction mode drives the ARRANGEMENT, not just click behaviour (**D-0 extended**)」

而被它「extended」的 D-0 原文（[[03-product-spec#4.0.7]]）写的是：

> **作用范围**：点击语义变更**仅限 Scene 话术卡**；Macro 区、最近使用区、搜索结果等复制入口不随模式变化。

[[023-ui-reshape-before-release]] 只裁决了「发布前做一次系统性重塑」与「范围 = UI + 组件架构」，**通篇未涉布局形态**；`docs/plans/ui-reshape.md` 全文 grep「调用态 / 整理态 / arrangement」**零命中**。

**dual-layout 是实现阶段自行扩张的，既无 ADR 也无 plan 条目，仅存在于一行代码注释里。**

### 事实二：调用态骨架同时违反三处已批准契约

| 契约 | 原文 | 调用态实现 | 判定 |
|---|---|---|---|
| [[03-product-spec#4.0.7]] 作用范围 | 模式只改点击语义，仅限 Scene 话术卡 | 改整页区域编排 | ❌ 越界 |
| [[03-product-spec#13.3]] 区域 6 位置 | Modifier「aside 列顶部（最近使用之上）」 | 底部通栏 tray（`Dashboard.tsx:125`） | ❌ 不符 |
| [[03-product-spec#13.4]] Tab cycle | 相位带 / 对齐话术 / Macro / **Scene / 最近** / SOP | 相位带 / 对齐话术 / Macro / **最近 / Scene** / SOP | ❌ 顺序颠倒 |

第三条已被测试固化：`App.test.tsx:205-206` 的注释写着「**03-product-spec §13.4 order update pending human review**」——即实现明知自己与契约不符，用一条「待人审」注释挂账，同时钉了两条断言分别锁住两种模式的不同顺序（`:218` 与 `:239`）。**测试在保护偏差本身。**

### 事实三：区域位移的实际规模

| 区域 | 调用态 | 整理态 | 位移 |
|---|---|---|---|
| Macro | 左列（吃满热区） | 左列（200px cap strip） | 同列，尺寸剧变 |
| 最近使用 | **左列下** | **右列中** | 跨列 |
| Scene | **右列上（context rail）** | **左列下（主区）** | 跨列 |
| Modifier | **底部通栏** | **右列上** | 跨结构 |
| SOP | 右列下 | 右列下 | 不变 |

五个区域里三个跨列移动。此外两态各持一个独立的 localStorage 分栏宽度键（`cockpit-2col` / `panorama-2col`，`Dashboard.tsx:46-53`），列宽也各记各的。

**一次模式切换 = 三区跨列 + 一区尺寸剧变 + 列宽基准更换。** 这已经不是"同一个界面的两种状态"，是两个界面。

### 事实四：调用态里有一项不能丢的真实收益

2026-08-10 的命中率重分配（CHANGELOG 同日条目）是有实测支撑的正确决策：Macro 由 200px 硬 cap 改为吃满热区，可见卡片 3.5 张 → 8.5 张。**这项收益目前只存在于调用态**，整理态的 Macro 仍受 `--h-macro-strip` cap。

因此本决策**不能**简单地"废掉调用态、保留整理态"——必须在单一布局里保住这项收益。

### 业务约束

- [[02-constitution#C1]] 200ms 唤起：删掉一个条件分支只会更快，无风险
- [[02-constitution#B2]] 协议 / 任务物理分离：ProtocolBand 独立于 panorama，本决策不触
- [[01-spec]] 哲学二「看见全局」：六区同屏不可减——本决策只重排，不隐藏任何区域
- [[03-product-spec#4.0.5]] 边界注：主形态整理态承接**轻量**整理，批量 / 结构性整理仍归辅形态——轻量整理不需要一套专属布局

### 不决策的代价

- 空间记忆无法形成：这是仪表盘类产品最核心的资产，且损耗随使用频次累积
- Tab 顺序随模式变化，键盘肌肉记忆一并失效（不只是鼠标问题）
- 两套布局 = 每个新区域要设计两次、测试两次、走查两次；已经能看到成本（`--macro-strip-cap` 这类"同一组件在两态下由父容器决定高度"的间接层）
- 契约与实现的偏差被测试固化，时间越久越难分辨"哪个是对的"

## 4. Options Considered

### Option A: 维持双布局（现状）

- **描述**：承认 dual-layout，补开 ADR 追认，并把 §4.0.4 / §13.3 / §13.4 三处契约改写为「按模式分列」。
- **优点**：零代码改动；每种模式的空间分配都可针对该模式最优化。
- **缺点**：空间记忆与 Tab 记忆的损耗是**结构性**的，不因追认而消失；三份契约都要分叉成两栏，后续每个区域的位置字段都要写两遍；「模式」这个词继续承担两种不同量级的含义（语义切换 vs 界面切换）。
- **预估成本**：0 天代码 + 约 1 天文档分叉，交付一个把偏差写进契约的结果。

### Option B: 固定单布局，模式只改语义（选定）

- **描述**：删除 `Dashboard.tsx` 的 `cockpit ?` 分支，两态共用一套空间；模式差异收敛回 §4.0.7 原本的作用范围（点击语义 / 动作簇显隐 / suppressHide / 编辑入口）。纵向分配改为用户可拖拽并持久化，以保住 2026-08-10 的命中率收益。
- **优点**：三处契约违规一次性归零，且**不需要修改契约**——回到契约即可；空间与 Tab 记忆恒定；新区域只设计一次；`Dashboard.tsx` 减约 45 行、`Dashboard.module.css` 的 cockpit 段整段并入；「一套布局 + 用户可调」比「两套布局」表达力更强，因为它承认了偏好是连续的而非二值的。
- **缺点**：任一模式都拿不到"专为该模式最优化"的空间分配，取而代之的是一个折中默认值 + 用户自行调整；已习惯当前双布局的用户（目前只有 omar）需要一次重新适应；新增一个可拖拽维度意味着新的持久化状态与新的极端窗口尺寸测试面。
- **预估成本**：约 1 天代码 + 0.5 天契约回流。

### Option C: 承认为两个工作区（workspace）

- **描述**：不叫"模式"，改叫两个工作区，各自独立布局，加显式切换叙事（过渡动画 / 独立入口 / 独立标题）。
- **优点**：诚实——如果界面确实是两个，就不要假装是一个的两种状态；重排从"意外"变成"预期"。
- **缺点**：与 [[03-product-spec#4.0.5]] 冲突——整理态的定位是"顺手整理一条"的轻量承接，为它建一个完整工作区是量级错配，深度整理本就归辅形态；「一屏全景」的学习成本按工作区数量翻倍；主形态是唤起即走的形态，容纳不下两个工作区的心智。
- **预估成本**：2 天以上，且要改 §4.0.5 的形态分工。

### Option D: 最小止血——只把 Modifier 归位

- **描述**：只撤掉调用态的底部 Modifier tray（最刺眼的一处），其余重排保留。
- **优点**：半天完成；解掉三处违规中的一处。
- **缺点**：Scene 与最近使用的跨列位移原封不动——**空间记忆的损耗主要来自这两个**（Modifier 不在 Tab cycle，且是最低频区）；Tab 顺序违规未解；一年后没人记得为什么只有 Modifier 被归位了。
- **预估成本**：0.5 天，交付一个不解决主要问题的中间态。

## 5. Decision

> **一句话拍板**：选 Option B —— 两态共用一套空间布局，`interactionMode` 回归 §4.0.7 既定的作用范围（只改交互语义），纵向分配由用户拖拽决定而非由模式决定。

**为什么不选其他**：

- 不选 A 因为：它把一处从未经过决策的实现扩张，追认成三份契约的永久分叉
- 不选 C 因为：为轻量整理建一个完整工作区，与 §4.0.5 的形态分工量级错配
- 不选 D 因为：它修的是最显眼的一处，不是损耗最大的一处

### 子决策 1 — 单一布局以**现整理态骨架**为基底

左列：Macro（上）/ Scene（下）；右列：Modifier（上）/ 最近使用（中）/ SOP（下）。

理由不是审美偏好，而是**它已经同时满足两处契约**：Modifier 落在 §13.3 规定的 aside 列顶部；DOM 顺序解析为 `macro → scene → recent → sop`，与 §13.4 Tab 顺序逐位一致。调用态骨架三处越契约，不具备作基底的资格。

### 子决策 2 — 用「一套布局 + 用户可调纵向分配」取代「两套布局」

保住 2026-08-10 命中率收益的正确做法不是为它保留一整套布局，而是**把分配权交给用户**：

- 左列 Macro / Scene 之间插入 `Separator`，复用 [[016-choose-dnd-and-resizable-layout]] 已在用的 `Group` / `Panel`（新增纵向 Group，非新依赖）
- 默认值偏向 Macro（命中率证据），但下限保证 Scene 至少完整显示一个子阶段列

> **本条的验收条件曾未被满足（2026-08-19 修正）**：首版实现取 `196px`，实测下 Scene 显示 **0 条话术**——清掉了结构 chrome 却没留下任何内容，且 `ScenePanel` 隐藏滚动条，区域读起来像「空」而非「可滚动」。**这不是取舍分歧，是没达到本子决策白纸黑字的验收条件**。已改为 `288px`：区域头 + tab 行 + 卡头（224）+ 第一张话术卡完整（→265）+ 第二张卡露边（→288）。两个区域的下限自此语义一致——**一个完整单元 + 下一个露半截**，露出的半截即「下面还有」的提示，故不引入渐隐或箭头（不新增视觉语汇）。
- `--macro-strip-cap` / `--h-macro-strip` 退役：高度不再由父容器按态注入，改由用户持久化的拖拽值决定
- 拖拽值与列宽同规格持久化到 localStorage（**不进 SQLite、不上传**，守 [[02-constitution#A2]]）

**这是本 ADR 的核心置换**：二值的"模式"承担不了连续的空间偏好；把它交给一个连续控件，两套布局的存在理由随之消失。

### 子决策 3 — 分栏宽度持久化键合一

`cockpit-2col` 与 `panorama-2col` 两个 `useDefaultLayout` 合并为单一 id。**旧键不迁移、不清理**——纯 UI 偏好，读不到即回落默认值，无数据风险；写迁移代码的成本高于它的价值。

### 子决策 4 — 模式差异的最终清单（= §4.0.7 原范围，不增不减）

| 维度 | 调用态 | 整理态 |
|---|---|---|
| Scene 话术卡整卡点击 | 复制 | 选择 / 预览 |
| 复制后窗口 | 200ms 隐藏 | 驻留（usage 照计） |
| 动作簇 | 不显（[[025-unified-anchored-editing]] 子决策 3.3 后为"仅选中项显"） | 选中项常显 |
| 编辑入口 | 不外露 | 外露 |
| **区域位置 / 列宽 / 区域尺寸** | **完全一致** | **完全一致** |

最后一行是本 ADR 的全部内容。

### 子决策 5 — Tab 顺序按 §13.4 收口，删除分歧测试

`App.test.tsx` 现有两条按模式分别断言 region order 的测试合并为一条：**无论模式，DOM 顺序恒为** `phase-bar → alignment-phrases → macro-grid → scene-panel → recent-list → sop-progress → status-bar`。`:205-206` 的「pending human review」注释随之删除——不再有待审的偏差。

### 两项一并浮出、但本 ADR **不裁**的待决项

1. **`任务层` pill 的去留**：现仅整理态渲染（`Dashboard.tsx:145-150`）。两态统一后必须二选一（常显 / 删除）。外部评价主张删（解释性 UI），但它与 ProtocolBand 的「协议层」pill 成对，删一半会破坏层级编码对称性——属视觉契约，归 [[05-design-spec]] 回流时裁。**本 ADR 先按"常显"实现以保持行为等价，不夹带视觉决策。**
2. **SOP stub 是否继续占正式区**：`SopProgress` 实现为单行 stub 而 §13.4 描述为 instrument card，此偏差在 [[HANDOFF]] 已挂账。它与布局固定与否正交，不并入本 ADR。

## 6. Consequences

### 正向后果

- 三处契约违规归零，且**通过回到契约实现，不需要修改任何契约条文**（§4.0.4 表格需重写，但那是把 reshape 后的事实补正，不是为偏差让路）
- 空间记忆与 Tab 记忆恒定：Macro 永远左上，Scene 永远左下，Modifier 永远右上
- `Dashboard.tsx` 删除条件分支约 45 行；`Dashboard.module.css` 的 `.cockpitMain` / `.cockpitRail` / `.modifierTray` 三段并入主布局
- `--macro-strip-cap` 这层"父容器按态注入子组件高度"的间接寻址消失，`MacroGrid` 重新自洽
- 新增区域从此只需设计一次、测试一次、走查一次
- 空间偏好从二值升为连续，表达力净增

### 反向后果

- **任一模式都不再拥有"为该模式最优化"的空间分配**。若日后证明某态确实需要显著不同的分配，本决策要付一次回退代价
- 新增一个可拖拽维度 = 新的持久化状态 + 新的极端尺寸测试面（这正是 [[HANDOFF]] 里 `.cockpitMain > :last-child` 无像素下限那笔挂账的同类问题，**本决策必须一并解掉而不是复制它**）。**2026-08-19 已实测解掉**：两下限真实生效，触发阈值为窗口高 `592px`，低于任何现实显示器；起草时引用的「640px 基线窗口」经核实不可复现，详见 §2
- 已适应当前双布局的用户（目前只有 omar）需要一次重新适应
- 与 [[025-unified-anchored-editing]] 的 P2 键盘动作层同批改 `App.test.tsx` 与 Dashboard 结构，**两者有编辑冲突面**——建议本 ADR 先落，025 的 P1/P2 在固定布局上迁移
- 删掉的两条模式分歧测试是"负向覆盖"（它们锁的是应当消失的行为），但删测试永远需要显式记录，故在此留档

### 未来反悔成本

- **代码改造规模**：3 个文件 + 测试，约 150 LOC；回退 = revert 单个 commit
- **数据迁移**：无。localStorage 旧键留在原地，schema / IPC 不动
- **不可逆点**：**无**。布局是纯前端渲染决策，不写库、不进协议——这是本 ADR 与 025 的关键区别，可以低风险地先落地再验证
