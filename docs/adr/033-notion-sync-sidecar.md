# ADR-033：Notion 提示词库与应用自动同步

## 1. 标题与日期

- **标题**：用独立同步进程连接 Notion 提示词库与本机库，按字段划分写入方
- **日期**：2026-11-15
- **决策者**：HuiW86（方向口头裁决 2026-11-15：接受「内容只在 Notion 改」，要求应用里保留一个修改提示并能跳转到 Notion；确认 2026-11-02 之后没有在应用里改过内容）
- **影响范围**：[[02-constitution#A2]] 需补一句例外（人主笔，本 ADR 只给出建议措辞）/ 新增 crate `prompt-hub-sync` / 新增一张本机表与一次 migration / `repo-write` 新增按 id 合并写入 / 「管理」工作区编辑入口 / 签字后回流 [[06-prd]]、[[03-product-spec]]、[[10-ops-spec]]；推翻 [[031-panorama-default-view]] Option D 的否决理由（031 本身不改）

## 2. Status

`Proposed`

- 待 HuiW86 签字。裁点只有一个，见 §5「送审」。
- 开工时间：M-01 复盘之后（2026-11-12 冻结决定），排在技能 Tab P1（issue #28）之前。

## 3. Context

- **触发事件**：2026-11-14 HuiW86 问「有没有办法让提示词自动同步更新」。
- **现状（2026-11-14 实查）**：
  - Notion 库 76 条，其中 3 条没有本地 ID（2026-11-05 / 11-06 / 11-09 新建），应用里没有，最久已 9 天。
  - Notion 的「最近使用时间」停在 2026-11-02，此后应用里的复制计数一次也没回到 Notion。
  - 2026-11-02 一次性导入之后，没有发生过任何导出或导入。
  - 现有导入（`repo_write::import::import_json`）是整库清空再写入，`usage_records` 在清空名单里：每导入一次，逐次使用流水丢一次。
- **与 ADR-031 的关系**：031 的 Option D「应用内做 Notion 同步」被否决，理由是「违反 A2，且文件交接未被证明不够用」。后一半已被上面的数据推翻：手动交接靠人记得去做，实际一次没做，两边已经分叉。前一半仍然成立，所以本 ADR 不把同步放进应用，而是放进独立进程，并正面处理 A2。
- **业务约束**：
  - [[02-constitution#A2]]「不依赖云同步」，CLAUDE §6 第 5 项「不要把数据上传到任何外部服务」。
  - 全景决策原则 3：位置只由用户指定。原则 5：取用必须经过面板，计数才完整。
  - [[02-constitution#C1]]：唤起 ≤ 200ms P95。
  - Notion 数据源的描述已写明「2026-11-07 起以 Notion 为准」，ADR-032 也称其为主副本——内容本来就由用户自己放在 Notion。
- **不决策的代价**：Notion 里新写的条目进不了全景；Notion 里的使用次数是旧数，按它做的复盘是错的；将来任何一次手动导入都会清掉使用流水。

## 4. Options Considered

### Option A：维持文件交接

- **描述**：继续「Notion 导出 → 应用导入」的手动流程。
- **优点**：零开发；A2 无争议。
- **缺点**：12 天内一次未执行；导入会清掉 `usage_records`。
- **否决原因**：已被数据证明不工作。

### Option B：应用主进程直接调 Notion API

- **描述**：在 Tauri 进程里定时拉取、推送。
- **优点**：少一个二进制。
- **缺点**：联网逻辑进入唤起路径所在的进程，token 与网络错误进入 UI；A2 的边界从「应用不联网」变成「应用联一部分网」，以后难守。
- **否决原因**：边界不清，C1 风险。

### Option C：定时让 AI 代理对账（Notion MCP + `prompt-hub-mcp`）

- **描述**：定时任务唤起一个 AI 会话，两边读一遍后写入。
- **优点**：不写同步代码。
- **缺点**：确定性的对账交给 LLM，结果不稳定且每次有成本；`prompt-hub-mcp` 的写工具只能写草稿区，改不了已有条目，也回写不了计数。
- **否决原因**：不可靠，且能力不够。

### Option D：双向编辑加冲突合并

- **描述**：两边都能改内容，按时间戳或三方合并解决冲突。
- **优点**：两边都能编辑。
- **缺点**：复杂度高一个量级；合并错了丢的是提示词正文。
- **否决原因**：按字段划分写入方之后根本不会有冲突，不需要它。

### Option E：独立同步进程，按字段划分写入方 ✅

- **描述**：新增二进制 `prompt-hub-sync`，由 launchd 每 5 分钟运行一次。内容字段只由 Notion 写，使用计数只由应用写，全景布局不同步。应用主进程不联网。
- **优点**：结构上没有冲突；应用不依赖同步（关掉同步器应用照常工作）；沿用 [[015-expose-mcp-write-pipeline]] 已验证的「独立进程 + 共享 `repo-write`」模式。
- **缺点**：多一个二进制要打包、签名、安装；需要给 A2 补例外；应用里不能再直接改内容。
- **预估成本**：1 个 crate（约 600–900 行含测试）、1 次 migration、应用侧 2 处改动、launchd 安装步骤。

## 5. Decision

> **一句话拍板**：选择 Option E——独立进程定时同步，每个字段只有一个写入方。

### 子决策

1. **字段归属**

   | 字段 | 写入方 | 方向 |
   |---|---|---|
   | 名称、正文、类型、工作阶段、场景、子阶段、分组、角色、任务、备注、已弃用等全部内容与分类字段 | Notion | Notion → 本机 |
   | 使用次数、最近使用时间 | 应用 | 本机 → Notion |
   | 全景位置与常用位（`panorama_placements`） | 应用 | 不同步 |
   | 本地 ID | 新建时生成一次 | 写回 Notion 后不再改 |

2. **类型映射**（以 2026-11-02 导入时写入 Notion 的 ID 字段为准）

   | Notion「类型」 | 本机表 | 依赖的 ID 字段 |
   |---|---|---|
   | Modifier | `modifiers` | — |
   | Composition | `compositions` | 阶段 ID |
   | Macro | `macros` | — |
   | 场景话术、快捷指令 | `phrases` | 场景 ID、子阶段 ID |
   | 协议话术 | `alignment_phrases` | 阶段 ID、层级 / 模式 / 领域 ID |

   场景、子阶段、相位、轴取值这些结构表不由同步器创建：Notion 行引用了本机不存在的 ID 时，这一行跳过并记入错误，不猜。

3. **新建两边都可以**。Notion 里没有本地 ID 的行：本机创建后把本地 ID 写回 Notion。本机有而 Notion 没有的条目（例如 MCP 草稿转正）：在 Notion 建一行。

4. **删除只做软删除**。Notion 行被删除或勾了「已弃用」→ 本机走 [[028-reversible-delete]] 的软删除，可在废纸篓恢复。同步器从不硬删。

5. **每次运行全量、幂等、无游标**：拉全库 → 按本地 ID 对账，内容哈希未变的跳过 → 按 id 合并写入本机 → 回写有变化的计数。`repo-write` 新增按 id 增改的合并写入，不清空任何表；`usage_records` 与 `panorama_placements` 不在写入范围内。

6. **本机状态表**：新增 `sync_links(asset_kind, asset_id, notion_page_id, content_hash, pushed_usage_count)`，migration 编号开工时按当时的 `user_version` 顺延（现为 17）。它属于本机状态，与 `settings` 一样不进导出，导出 data schema 不变。五张资产表不加列。

7. **三道保险**
   - 首次运行只出差异报告，不写入；用户确认后才开始自动同步。
   - 单次运行要软删除的条目超过 20% 时中止并报错，本机零改动（防 token 失效或权限变化导致 Notion 返回空）。
   - 有写入的运行，写入前先做一次快照（复用 `repo_core::backup`，独立前缀与配额）。

8. **凭据与调度**：Notion internal integration token 存 macOS 钥匙串，integration 只授权提示词库一个数据库。launchd 每 5 分钟一次、登录时一次。不做常驻进程，不做 webhook。同步默认关闭，由用户显式开启。

9. **应用侧改动只有两处**
   - **唤起时刷新**：唤起时读 `PRAGMA data_version`，变了才重新加载数据。附带解决 HANDOFF 第 21 项「隐藏期间 MCP 写入的草稿唤起不刷新」。须附 `pnpm bench:hotkey-wake` 结果。
   - **编辑入口改为提示加跳转**（HuiW86 2026-11-15 要求）：同步开启后，「管理」工作区里内容编辑入口的位置不变、仍然可见；点开后不进编辑器，而是显示一句「内容在 Notion 维护」和一个「去 Notion 修改」按钮，按钮打开该条目的 Notion 页面。还没有对应 Notion 页面的条目（尚未同步到）显示「等待同步」。同步关闭时，编辑器照旧可用。全景面板不放任何同步信息。
   - 设置弹窗 · 数据页加一组「Notion 同步」：开关、最后成功时间、最后一次错误。连续失败超过 24 小时，Header 的设置入口显示一个小点。

10. **同步器不做的事**：不推送 `usage_records` 流水（Notion 只收累计值）；不同步全景布局；不创建结构表；不处理内容冲突（不存在）。

### 送审（唯一裁点）

**宪法 A2 是否补一句例外。** 同步器会把两类数据写到 Notion：使用次数与最近使用时间；以及在本机新建、Notion 还没有的条目正文。按 A2 与 CLAUDE §6 第 5 项的字面，这属于「上传到外部服务」，不改宪法就不能做。

- **推荐：补例外。** 建议的意思（措辞由 HuiW86 定，宪法是人主笔文档）：「用户自己指定为主副本的 Notion 提示词库除外：可由独立同步进程读写，默认关闭；应用主进程仍不联网，关闭同步后应用功能完整。」证伪条件相应补一条：「见到应用主进程发起网络请求（更新检查除外）→ 违反」。
- **理由**：这些正文本来就是用户自己写在 Notion 里的，同步没有把数据带到新的地方；A2 要守的三件事（无运维、无网络依赖、无新增隐私暴露）在「独立进程 + 默认关闭 + 应用可离线」下都还在。
- **不补的后果**：只能做单向（Notion → 本机），使用次数回不到 Notion，本机新建的条目也进不了 Notion。

### 为什么不选其他

- 不选 A：12 天零执行，且导入丢流水。
- 不选 B：联网进主进程，边界守不住。
- 不选 C：不确定、有成本、写不了已有条目。
- 不选 D：没有冲突可解，白付复杂度。

## 6. Consequences

### 正向后果

- Notion 里改一条或新建一条，几分钟后应用里就有；应用里的使用次数几分钟后回到 Notion。
- 不再需要整库导入，`usage_records` 不再被清。
- 技能 Tab（issue #28）可以把 Notion 技能索引当作第二个数据源接进同一个同步器，不必另做手动导入。
- HANDOFF 第 21 项的唤起不刷新一并解决。

### 反向后果

- 同步开启后应用里不能直接改内容，改一个字也要去 Notion；Notion 打不开时改不了（但仍能用）。
- 内容变更最长有约 5 分钟延迟。
- 多一个二进制与一份 launchd 配置，安装与卸载步骤要写进 [[10-ops-spec]]。
- 宪法 A2 多一条例外，以后看到「联网」要先分清是哪个进程。
- Notion 数据库的列名与选项成为接口：在 Notion 里改列名会让同步报错（报错而不是写坏数据）。

### 未来反悔成本

- **代码**：删掉 `prompt-hub-sync` crate 与应用侧「提示加跳转」分支即可，编辑器原样保留着。
- **数据**：`sync_links` 表可以留着不用。带新 `user_version` 的库不能交给旧版本打开，这是唯一不可逆点。
- **Notion 侧**：回写的只是两列计数与本地 ID，不同步后它们停在最后的值，不需要清理。

## 7. 验收标准

1. 在 Notion 改一条正文，6 分钟内唤起应用，复制出的是新正文。
2. 在 Notion 新建一条，6 分钟内出现在全景；该 Notion 行自动带上本地 ID。
3. 在应用里复制 3 次，6 分钟内 Notion 的使用次数加 3、最近使用时间更新。
4. 同步前后 `usage_records` 行数不变，全景常用位不变。
5. token 失效时运行一次：本机零改动，设置页显示错误。
6. 断网时唤起、复制、记数全部正常。
7. `pnpm bench:hotkey-wake` P95 无回归。
8. 同步开启时点编辑入口：出现提示与「去 Notion 修改」，按钮打开的是这一条的 Notion 页面；同步关闭时进入原编辑器。
