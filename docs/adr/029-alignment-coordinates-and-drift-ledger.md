# ADR-029: 对齐坐标与漂移账（四轴落进现有相位 + 中途口令隐式记账）

## 1. 标题与日期

- **标题**：「开场对齐台」的四轴坐标接进现有数据模型——**Phase 表一行不改**，形态六段落成六条普通 AlignmentPhrase 分入现有相位；`alignment_phrases` 新增三列可空坐标（抽象层 / 闭环域 / 模式），复制时拼成一句前缀再接 content；六条中途口令同样是 AlignmentPhrase，**每一次复制本身就是一笔漂移账**，不新增任何「这次出问题了」按钮
- **日期**：2026-09-04
- **决策者**：omar（2026-09-04 拍板问题一、二）；起草：Claude（🤝 共创文档，见 [[CLAUDE#§5.2]]）
- **影响范围**：
  - **数据**：migration `0014`（`user_version` 13→14）——`alignment_phrases` 加 `layer` / `domain` / `mode` / `content_revised_at`；新增可配置的轴取值小表；`usage_records.source` 的 CHECK 增列 `live_cue`（SQLite 改 CHECK 必须整表重建，见 §3 约束 3）；并入 [[HANDOFF]] 21.1 的唤起时间戳
  - **代码**：`repo-core/src/models.rs` 的 `AlignmentPhrase` 与 `UsageSource`；`repo-core/src/export.rs`（`DATA_SCHEMA_VERSION` 1.2→1.3）与 `repo-write/src/import.rs`；对齐话术的复制路径拼前缀；状态仪表区新增按轴计数
  - **文档**：[[06-prd]] §6.6 字段表 / §6.8 `source` 枚举 / §6.9 导出 schema、[[03-product-spec]] §13.3 区域 2-bis 与区域 7、[[07-features]] 矩阵新增行、[[11-test-spec]] 常规回流
  - **spec**：回答 [[01-spec#10.4]] 开放问题第四问（「是否需要相位转场话术」）——**需要，但它不是 Phase 之间的过渡对象，是一类普通对齐话术**
  - **ADR**：新增 `usage_records.source` 枚举值一次，与 [[011-search-usagesource]] 预留的同族问题相邻但不替代它

## 2. Status

`Accepted`（2026-09-04 omar 拍板：问题一「六段与八相位的关系走路径 A」、问题二「感知信号走隐式记账」，五条子决策同日照签，未落地）

> **范围声明**：本 ADR 只裁**坐标怎么存、口令怎么记账**。**显式不裁「8 相位是不是切错了」**——四轨与 8 相位是两套刀法，本 ADR 让两套并存并开始记账，重切与否留给账跑出来之后（§5「显式不裁」第 1 条）。**也不裁任何形式的自动判断**——那是 [[01-spec#8.1]] 的永久禁令，不是「等」。
> **实施期口径（2026-09-04 图纸回流时定，ADR 正文未设想或写作「由实现定」的八处；照 [[028-reversible-delete]] §2 的做法在此备案，不改上文）**：
>
> **口径 1 — 中途口令挂在新增的第 9 相位「中途」，并同时加 `kind` 列。** 子决策 3 把归属写成「挂相位或加 `kind`」二选一，实际两条都走：seed 加一行 `phase-live`（name「中途」，order_index 8），六条口令是它的对齐话术（`kind = 'cue'`），默认话术为「停」，`⌘9` = 切到「中途」+ 复制「停」+ 复制即隐藏。这样 [[01-spec#3.5]]「每条对齐话术必须归属一个 Phase」一字不动、`phase_id` 仍必填。**代价两条，正文没写**：① 上文反复说「`phases` 表零改动」，对表结构成立，对 seed 不成立——出厂相位从 8 个变 9 个，spec §3.5 那张人主笔的相位表列的仍是 8 个，是否回流由 omar 定；② 按 `⌘9` 之后状态栏「当前相位」与后续 `usage_records.phase_id` 都变成「中途」，而用户实际做的事没变。归因计数不受影响（它按会话内先后配对，不看当前相位），但相位使用分布会多出一格「中途」。不加「用完自动切回」这类补丁。
>
> **口径 2 — 坐标三列存 id 不存名字**：`layer_id` / `domain_id` / `mode_id`，FK → `alignment_axis_values.id`，`ON DELETE SET NULL`。上文写的 `layer` / `domain` / `mode` 是列的语义名。改名不会让话术上的坐标失效。
>
> **口径 3 — 口令到轴的映射单开一列 `cue_axis`**，不复用三列坐标：形态轴没有列可复用（形态由 `phase_id` 承载），且三列坐标在复制路径上已有含义，复用会让「本轮只谈商业闭环」被复制成前缀加它自己。因此 `alignment_phrases` 新增**六列**不是五列（`kind` / 三列坐标 / `cue_axis` / `content_revised_at`）。
>
> **口径 4 — `alignment_axis_values` 不是资产表**：无 `deleted_at`，硬删，不进第七道闸门（§6「由实现确认」就此确认）。硬删不可逆，按 [[025-unified-anchored-editing]] `:125` 应当行内确认，`ConfirmInline` 消费者从 1 处变 2 处。
>
> **口径 5 — 八个「常用档位」不 seed**，只 seed 六条形态话术（坐标全空、非默认）。档位是用户自建的带坐标话术行。
>
> **口径 6 — 模式轴可空**（子决策 2 边界自检 ③ 交给 UI 的那项）：不可空的轴会逼用户在不重要时也编一个值，编出来的值进账会把归因喂脏。
>
> **口径 7 — `usage_records.source` 的语义被重载**：它原是「触发入口」，`live_cue` 是话术类别——口令从最近使用区复制也记 `live_cue` 不记 `recent`。不另开一列，因为 append-only 表加列比重载一个值更贵，且归因只关心「是不是口令」。prd §6.8 显式重述这一列的定义。
>
> **口径 8 — 导出顶层键是 `alignment_axis_values`**（snake_case），`ExportBundle` 无 `rename_all`，十个既有顶层键全是 snake_case，只有行内字段是 camelCase。IPC 预计 56 → 62（轴取值五个 + `summarize_drift_ledger`），实测以落地时 IPC gate 为准。

## 3. Context

### 触发事件

omar 2026-09-04 拿出一个单文件原型 `docs/mockups/开场对齐台.html`：四轨（形态 / 抽象层 / 闭环域 / 模式）+ 六段形态话术 + 八个常用档位 + 六条中途口令 + 六条跨层规则。它解决的是本项目至今没解决的一件事——**对齐不只发生在开场，漂移发生在中途**，而现有相位带只管开场那一下。

### 两套刀法不一样，这是必须先说清的事

| | 现有 8 相位（[[01-spec#3.5]]） | 开场对齐台四轨 |
|---|---|---|
| 切法 | 一维：发散 / 理解 / 规划 / 生成 / 执行 / 收敛 / 沉淀 / 迭代 | 四维正交：形态 × 抽象层 × 闭环域 × 模式 |
| 混了什么 | **「模式」与「产出契约」两个维度混在一条轴上**——「发散」是模式，「生成」是产出形态 | 二者被拆到不同轨（模式轨只有发散 / 收敛 / 侦察） |
| 缺什么 | **「挑错」没有座位**——它既不是收敛也不是迭代，是一种独立的协作形态 | 抽象层与闭环域在 8 相位里根本没有对应物 |

**本 ADR 不判哪套对。** 判定依据只能是使用数据，而数据要等本 ADR 先把账建起来才有。这是用闭环本身裁这个问题，不是回避它。

### 技术约束（全部经代码核实）

1. **8 相位与 8 条默认话术都在 seed 里**（`0002_seed.sql:6` 与 `:16`），`phases` 表可配置增删但至今没人改过。每相位恰好一条 `is_default = 1`，由 `idx_alignment_phrase_one_default_per_phase` 保证唯一。
2. **`alignment_phrases` 的 `notes` 列有字段、有类型、进导出，但从未有写入方**——create 恒写 `None`（`repo-write/src/alignment_phrases.rs:54`），没有 update 路径。prd §6.6 把它写作「迭代说明」，是本 ADR 子决策 5 现成的落点。
3. **`usage_records.source` 是带 CHECK 约束的 TEXT 列**（`0001_initial.sql:135`，六个取值）。**SQLite 不能 ALTER 一个 CHECK**，加枚举值必须走整表重建（建新表 → 搬数据 → 删旧表 → 改名 → 重建三个索引）。这张表是全库最高频写入的表，重建是本 ADR 最重的一步数据操作。
4. **`usage_records` 里没有「会话」这个概念**，只有 `timestamp`（`repo-core/src/models.rs:237`）。「同一次唤起内」目前不可查，这正是 [[HANDOFF]] 21.1 要补的唤起时间戳。
5. **第七道源码级闸门只管七张带 `deleted_at` 的资产表**（`src/ipc/soft-delete-gate.test.ts:53`，注释明写没有该列的表「none of this gate's business」）。新增的轴取值表要不要进这个清单，取决于它要不要软删。
6. **`settings` 表明确不进导出**（`0012_settings.sql` 注释：machine-local configuration, not a portable asset）。轴取值表与它**不同类**——轴取值是用户内容，丢了等于丢掉自己的坐标系。
7. **导出现含 8 张资产表 + 两个顶层字段**，`DATA_SCHEMA_VERSION = "1.2"`（`repo-core/src/export.rs:19`），`check_schema_version` 按 MAJOR 比对（prd §6.9）。
8. **迁移前自动取快照**：任何待跑迁移之前 `db.rs:198` 会取一次 `pre-migrate` 快照——这是 `usage_records` 整表重建唯一的兜底。
9. **C1 200ms**：本 ADR 的任何路径都不在唤起路径上。拼前缀发生在复制那一刻，按轴计数发生在状态仪表区。

### 不决策的代价

原型继续留在一个 HTML 文件里，与仪表盘的数据、使用记录、导出全部隔绝——**这恰恰是哲学四要消灭的那种「挥发掉的操作」**（[[01-spec#2.4]]）。更贵的是：不建账就永远没有数据回答「8 相位是不是切错了」，那个问题会一直只能靠回忆吵。

## 4. Options Considered

### Option A：形态六段落进现有相位，坐标作为对齐话术的可空列 ✅

- **描述**：`phases` 表零改动。六段形态话术落成六条普通 AlignmentPhrase 分入现有相位（探讨→发散 / 定路径→规划 / 出资产→生成 / 改稿→迭代 / 执行→执行 / 挑错→收敛）。`alignment_phrases` 加三列可空坐标，复制时拼前缀。中途口令也是 AlignmentPhrase，复制时以新枚举值 `live_cue` 记账。
- **优点**：
  - **不动人主笔文档**——[[01-spec#3.5]] 的 Phase 定义一字不改，AI 不越 [[CLAUDE#§5.2]] 的界
  - 坐标**可空**，八条 seed 话术与用户已有的话术全部零迁移、行为不变
  - 四轴是**正交坐标**不是层级，不触 [[01-spec#8.4]]「Phase 下不允许再嵌套子 Phase」
  - 档位（原型里那八个）落成**带坐标的话术行**，不需要任何新对象
  - 账建起来之后，「要不要重切 Phase」从只能吵变成能等
- **缺点**：
  - **两套刀法并存，用户要同时看见两种分类**，这是真实的认知成本，不粉饰
  - 「挑错」被塞进「收敛」是**将就**，它在 8 相位里确实没有座位
  - `alignment_phrases` 主表变宽（三列坐标 + 一列时间戳）
- **预估成本**：migration 一支（含 `usage_records` 整表重建）；Rust 模型三处、导出导入两处；前端复制路径拼前缀、状态仪表区加计数；seed 六条话术；文档回流

### Option B：Phase 升级为四轴坐标模型，重切相位带

- **描述**：废掉一维的 8 相位，`phases` 换成四个轴，相位带改成四轨选择器。
- **优点**：刀法统一，「挑错」有座位，「模式」与「产出契约」不再混在一条轴上
- **缺点**：
  - **要动 [[01-spec#3.5]]**，那是 🧑 人主笔文档（[[CLAUDE#§5.2]]），AI 不得起草
  - 现有 8 条默认话术、`⌘1-8`（[[03-product-spec#13.4]]）、`phases.default_alignment_phrase_id` 冗余指针、`usage_records.phase_id` 全部要重新定义
  - **最要命的一条**：此刻没有任何数据说明四轨比 8 相位好，只有一个原型的直觉。用直觉推翻一个已 ratified 且实装的模型，是本项目一贯拒绝的做法
- **预估成本**：远高于 A，且不可逆——`usage_records.phase_id` 的历史一旦失去指代对象就再也回不来

### Option C：把整页 HTML 作为独立区域塞进仪表盘

- **描述**：把 `docs/mockups/开场对齐台.html` 原样嵌成一个新区域，与相位带并列。
- **优点**：当天可见，零数据模型改动
- **缺点**：
  - **违反 [[01-spec#8.7]]「不做两套独立 UI」**——它与相位带功能重复，用户要在两个地方切协作模式
  - 原型通篇裸 hex 与裸 px（`--c-form:#C9A227` 等），全部要 token 化才能进代码（[[CLAUDE#§4.1]]）
  - 它的复制不经 `record_usage`，**沉淀照样挥发**，等于没解决触发本 ADR 的那件事
- **预估成本**：最低，但不解决问题

### 感知信号子选项：显式按钮 vs 隐式记账

| | 显式「这次出问题了」按钮 | 隐式记账（选） |
|---|---|---|
| 用户动作 | 察觉漂移 → 额外按一次 | **零新动作**——复制口令本来就要做 |
| 信号质量 | 强、无歧义 | 弱，要从口令类别反推 |
| 依据 | — | [[01-spec#2.4]]「让沉淀成为使用的副产品」；[[025-unified-anchored-editing]] `:125`「撤销 > 确认」的同一精神：不给用户加动作 |
| 风险 | 90% 的漂移不会被按（哲学四对「独立沉淀动作」的原始论断） | **误判**：复制口令不等于出了问题，也可能只是正常换挡 |

**选隐式。** 但必须写明：「口令复制 = 一次漂移」是一个**未验证的假设**，本 ADR 建的是观测它的账，不是它的证明。若跑一段时间后噪音压过信号，再回来议显式按钮（§5「显式不裁」第 2 条）。

## 5. Decision

> **一句话拍板**：选择 **Option A**，理由是**它把四轴接进现有模型而不推翻任何已 ratified 的契约，并且它建起来的账，正是将来判定「要不要走 Option B」的唯一证据来源**。

**为什么不选其他**：

- 不选 B 因为：它要动人主笔的 [[01-spec#3.5]]，而支持它的只有直觉没有数据；A 跑一段时间之后，B 才可能成为一个可裁的问题
- 不选 C 因为：它与相位带功能重复（违 §8.7），且复制不记账——触发本 ADR 的那个问题原封不动

### 子决策

**子决策 1 — 形态六条入现有相位，`phases` 表零改动。** 六段形态话术落成六条普通 AlignmentPhrase：探讨→发散、定路径→规划、出资产→生成、改稿→迭代、执行→执行、挑错→收敛。**理解与沉淀两个相位本轮不接新话术**，它们的 seed 默认话术照旧。**代价说明白**：「挑错」放进「收敛」是将就——挑错要的是找出站不住的地方，收敛要的是从已有方案里选出最优解，二者只是都在做减法。这条将就本身就是最有价值的观测点：将来「挑错」这条话术的使用量若显著压过「收敛」默认话术，那就是 8 相位该重切的第一份证据。

**子决策 2 — `alignment_phrases` 加三列可空坐标，复制时拼前缀。** 新增 `layer` / `domain` / `mode` 三列，**全部可空，NULL 即「不限」**；非空时在复制那一刻拼成一句前缀「本轮在 X 层，只谈 Y 闭环，Z 模式。」再接 `content`。**存的是干净的 content，拼接发生在复制路径**——这样改坐标不算改内容（子决策 5 的切分点因此不被坐标调整污染），前缀格式将来要改也不必迁移任何行。轴取值存一张**可配置小表**（形如 `alignment_axis_values(axis, name, hint, order_index)`；表名与列由实现定，本 ADR 只定两件事：**可配置**，因为 [[01-spec#2.9]] 哲学九要求界面自身可维护；**随导出走**，因为它是用户内容，与明确不进导出的 `settings` 表不同类）。

> **三条边界自检**：① 四轴是**正交坐标不是层级**，不触 [[01-spec#8.4]]——档位就是一行带坐标的话术，**禁止**做成 Phase 下的子 Phase ② 加列不产生新资产类型，[[02-constitution#B1]] 的三层模型不动；轴取值表是配置表，与 `phases` 同类，不是第四层资产 ③ 原型的模式轨没有「不限」档，所以它的开场语总带模式；落库时三列一律允许 NULL，是否总给 `mode` 赋值由 UI 定。

**子决策 3 — 中途口令是 AlignmentPhrase 的一类，复制时记 `live_cue`。** 六条口令（换挡 / 换层 / 回到定位层 / 本轮只谈 X / 切收敛 / 停）落成 AlignmentPhrase，**归属方式由实现定**（挂在其语义对应的相位下，或给表加一列 `kind`）。它们留在协议层，因此 [[02-constitution#B2]] 的物理分离照旧适用——不入 Composition 工作台、不入 SOP、不进 Macro 区、不归 Scene，这条由第二道源码级 gate 继续守。复制时 `usage_records.source` 记新枚举值 `live_cue`。**零新按钮**：口令本来就要点一下复制，这一下同时就是记账。

**子决策 4 — 归因只能是计数，不能是判断。** 定义为：同一唤起会话内，「某条对齐话术被复制」之后出现的口令复制，**按轴归到那条话术头上计数**。展示在状态仪表区（[[06-prd#5.7]]，主形态即 [[03-product-spec#13.3]] 区域 7 状态栏；辅形态可展示更长周期，[[01-spec#8.7]] 明确允许这一差异）。会话边界依赖 [[HANDOFF]] 21.1 的唤起时间戳，两件事**合进同一支 migration `0014`**。

> **必须是计数不是判断**：[[01-spec#8.1]] 禁止「AI 自动判断当前相位」。展示「这条话术后面跟了 7 次换层口令」是记账；说「这条话术在层这一轴上不好」是判断。前者可以做，后者永远不做。
>
> **一处诚实的记账**：六条口令里只有五条归得到轴上——换挡 = 形态、换层与回到定位层 = 层、本轮只谈 X = 域、切收敛 = 模式，而**「停」不属于任何轴**，它是中止不是漂移。「停」照常记 `live_cue`，但不进任何一轴的计数。

**子决策 5 — 加 `content_revised_at`，用既有 `notes` 记修订说明，不做历史表。** 修订一条话术就是编辑 `content` + 写 `notes`（prd §6.6 的「迭代说明」，至今空转，见 §3 约束 2），同时刷新 `content_revised_at`。归因据此**切成前后两段**，完成「改了之后是不是真的少漂了」这一步再观测。**不做历史版本表**：那会把 [[028-reversible-delete]] 刚统一好的删除与恢复语义再复杂化一层，而本 ADR 要的只是一个切分点，不是完整版本史。**代价**是改第二次之后只剩最近一次的切分点，更早的分段不可回溯。

### 显式不裁

- **Phase 要不要重切**：等账。判据是子决策 4 的按轴计数与子决策 1 里「挑错」话术的使用量，**不是**任何人的直觉。重切必然要动 [[01-spec#3.5]]，届时由 omar 主笔
- **显式「出问题」按钮**：等隐式记账的噪音数据。若口令复制的信噪比低到不可用，再议
- **跨层规则六条**（原型 `<details>` 里那六条）：**不入库当资产**。它们是给人看的元规则，不是拿来复制粘贴给 AI 的话术，入库会把它们混进协议层资产统计。去向留给 omar（Vault 知识卡，或写进对应 phase 的 `description`）
- **AI 归因 / 自动判断漂移**：[[01-spec#8.1]] 永久禁止，**不是「等」**
- **[[011-search-usagesource]]**：搜索是否入 UsageSource 仍 Reserved。本 ADR 只加 `live_cue` 一个值，不顺手裁那个

## 6. Consequences

### 正向后果

- **漂移第一次可观测**。此前工具只在开场帮一下，中途出问题全靠人自己感觉；现在中途的每一次纠偏都留下一行
- **「使用即沉淀」延伸到协作过程本身**（[[01-spec#2.4]]），而不只是话术资产
- **回答了 [[01-spec#10.4]] 开放问题第四问**：相位转场话术需要，但它不是 Phase 之间的过渡对象，而是一类普通 AlignmentPhrase——这个答案顺带避免了给 Phase 引入「转场」这个新概念
- **给「8 相位是否该重切」建起了唯一可能的证据来源**，把一个只能吵的问题变成一个能等的问题
- **`notes` 列有了第一个写入方**，一个挂了很久的空字段销账

### 反向后果

- **两套刀法并存**，用户要同时面对 8 相位与四轴坐标。这是 Option A 的直接代价，只能靠账跑出来之后收敛，短期内不粉饰
- **`usage_records` 必须整表重建**（§3 约束 3）。这是全库最高频写入表，重建要搬全部历史行，且它不在软删除的保护范围内；唯一兜底是 `db.rs:198` 的 `pre-migrate` 快照
- **`usage_records.source` 加了 `live_cue` 之后语义不能再改**。这张表 append-only（[[06-prd#6.8]]），改一个已写入枚举值的含义会让所有旧账失真
- **`alignment_phrases` 主表变宽**四列。表本身很小（数十行量级），但每一列都要进模型、进导出、进导入、进 seed
- **隐式记账建立在一个未验证的假设上**：复制口令 ≈ 发生漂移。假设若不成立，收上来的是噪音而不是信号，而那要跑一段时间才知道
- **导出格式再次变更**，`DATA_SCHEMA_VERSION` 1.2→1.3。按 MAJOR 比对（[[06-prd#6.9]]），所以 1.2 与 1.1 的旧备份照常导入，无坐标的行反序列化为「不限」
- **第七道闸门的边界要复核**：轴取值表若被判定为资产表（要软删），必须进 `soft-delete-gate.test.ts:53` 的 `ASSET_TABLES`；若不软删则不进（§3 约束 5）。**由实现确认，本 ADR 不预判**

### 未来反悔成本

| 维度 | 代价 |
|---|---|
| **代码改造规模** | 三列坐标与 `content_revised_at` 留列不用即可；要下线的是复制路径的拼前缀、状态仪表区的按轴计数、轴取值表的配置 UI，约十余个文件 |
| **数据迁移** | 本项目 migration 是 forward-only，无需 down migration。但 `usage_records` 已被整表重建过一次，**那一步回不去**；已写入的 `live_cue` 行必须决定是保留还是清理 |
| **学习成本** | 无。不引入任何新依赖，不动 [[09-tech-stack]] |
| **不可逆点** | ① `usage_records` 整表重建一旦执行，旧表结构不再存在 ② `live_cue` 一旦写进历史账，语义就被冻住（append-only 表） ③ 三列坐标与轴取值表一旦进导出文件即进导入契约，改字段名要动 schema 版本 ④ 用户一旦开始按坐标组织话术，把坐标退回成自由文本是一次数据降级 |
