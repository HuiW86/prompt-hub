# ADR-033：技能索引与技能工作区

## 1. 标题与日期

- **标题**：在全景旁新增「技能」工作区，像取提示词一样取技能
- **日期**：2026-11-15
- **决策者**：HuiW86（需求与两项裁定 2026-11-14 于 issue #28：「单开」一个 Tab、阶段列交 AI 决定；2026-11-15「需求没有异议的话，帮我开始执行」；2026-11-15 在 PR #35 签字「同意」，单裁点「技能不进备份」按推荐通过）
- **影响范围**：migration `0018`（`user_version` 17→18）/ IPC 73→77 / 新工作区 `SkillPanel` / 签字后回流 [[03-product-spec]]、[[05-design-spec]]、[[06-prd]]

## 2. Status

`Accepted`

- Last reviewed: 2026-11-15（HuiW86 签字，单裁点按推荐通过；实现与图纸回流同在 PR #35）

## 3. Context

- **用户问题**（issue #28，2026-11-14 追问确认）：每天要找好几次技能，四个卡点全中——想不起有哪些、不知道该用哪个、不记得怎么叫、维护时找不到源文件。已装约 82 个（自建 13、Anthropic 自带约 12、Muse 内置 57）。
- **现状**：清单是 Notion 上一整页长文，只覆盖自建 13 个；源文件散在四处；技能用了多少次没有任何记录，哪些该退役无从判断。
- **同一个问题已经解决过一次**：提示词的「想不起、找不到、叫不出」就是全景（[[031-panorama-default-view]]）要解决的。技能的取用动作与之相同——看全、选一条、复制一句话、贴进对话。
- **约束**：不新增提示词资产类型（[[02-constitution#B1]]）；位置只由用户指定（ADR-031 原则 3）；唤起 ≤200ms（C1）；数据不出本机（A2）。

## 4. Options Considered

### Option A：把技能调用句当作提示词放进全景

- **优点**：零代码，P0 当天可做。
- **缺点**：76 条提示词加 82 个技能，一屏放不下，「一眼看全」失效；技能的「什么时候用 / 不用于 / 源地址」在提示词模型里无处安放。
- **否决原因**：只能作为过渡（issue #28 P0），不是终态。用户 2026-11-14 裁「单开」。

### Option B：独立技能库 + 复用全景看板 ✅

- **描述**：与常用网站（ADR-030）同类的独立库表；界面直接复用全景的列、层、按键与悬停卡；索引内容从外部文件导入。
- **优点**：用户已经会用全景，没有新东西要学；不触碰三层模型；代码量集中在一张表和一个视图。
- **缺点**：多一个工作区；索引要从外部导入一次。

### Option C：应用内编辑技能索引

- **否决原因**：技能的事实源在仓库、claude.ai 账号与 Notion，应用里再编一份就是第三份副本；改技能文字的频率远低于取用，不值得一个编辑器。

## 5. Decision

> **一句话拍板**：选 Option B——技能索引是一张独立库表，界面是全景看板的第二个实例；文字以导入文件为准，常用位与使用记录归应用。

### 子决策

1. **数据**：新表 `skills`（索引字段 + `pin_slot` + `order_index`）与 `skill_usage`（每复制一次一行，次数与最近使用时间由它算出）。枚举列在 Rust 校验、不写 CHECK——以后开一个新列应当是决策，但不该再付一次重建表。
2. **列**：六个阶段列「理解 / 发散 / 规划 / 生成 / 迭代 / 沉淀」，用全景同一套词、同一顺序。不开「收敛」「执行」：已知技能中没有一个主动叫的落在这两步（执行一步全是自动触发类）。一个技能只进一列，放在**叫它的那一步**。
3. **底部条**：自动触发类进「自动触发」，Muse 内置进「通用能力」（生活与办公事务，不是工作阶段），主动叫但没填阶段的进「未分阶段」——变暗不消失，不让任何已装技能凭空消失。`待试`、`已退役` 不上看板。
4. **按键与全景一致**：1–9 贴出常用位、方向键选择、↵ 贴出、打字筛选（名称 / 用途 / 什么时候用 / 调用句）、整理态 ⌥1–9 设常用位与 ⌥0 取消（让位带撤销）。唯一新增 **⇧↵ 复制源地址**——维护动作，不记数、不隐窗。复制内容是调用句，没有调用句时退回技能名。
5. **记数与隐窗**：每次复制写一行 `skill_usage`；调用态复制后隐窗、整理态驻留，与 `record_usage` 共用同一个隐窗计时器（同一个序号守卫，旧计时器不会误藏新唤起的窗）。
6. **导入**：`kind: "prompt-hub-skill-index"`、`version: 1` 的 JSON 文件即整份索引，整体成功或整体不动。文件里有的按 `id` 新增或更新（顺序即看板顺序），没有的删除（连同其使用记录——要留历史请把状态改成「已退役」）。常用位与使用记录不受导入影响；非「已装」的技能自动让出常用位。空索引、重复 id、未知阶段、超长字段一律拒绝。
7. **不进备份、不进废纸篓**：索引的事实源在外部，重新导入即可恢复；备份恢复既不清空也不回卷技能库（有测试）。这与 issue #28 原写的「导出 1.6→1.7」不同：去掉一层兼容口径，代价是换机时常用位与次数不随备份走（与 `usage_records` 不进导出同一口径）。
8. **不在唤起路径上**：技能视图按需加载，唤起仍落在全景，C1 路径一行未动。

## 6. Consequences

### 正向后果

- 技能与提示词同一种取法，第一次打开就会用。
- 技能第一次有了使用数据，复盘时可以按次数决定留、并、退。
- 「源地址」成为一键可得的交接物。

### 负向后果

- 索引要靠外部文件进来。现在由 Claude 从 Notion「技能索引」生成；若 Notion ↔ 应用同步器（2026-11-14 方案稿，尚未立项）落地，可以改为直接读 Notion，届时本 ADR 子决策 6 的文件格式保留为离线入口。
- Muse 内置 57 个需在本机读 `/opt/muse/skills/` 后补进索引；补进之前「通用能力」条为空。
- 列数与全景不同（6 对 8），同一个词在两边的横向位置不一样。

### 未来反悔成本

- 低：两张表与一个视图，不改任何既有表；删除只需一个反向迁移。
