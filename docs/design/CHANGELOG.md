# 设计文档变更日志

记录 prompt-hub 文档体系的每次修订，便于追溯决策演变。

格式约定：
- 每次修订记录日期、变更内容、变更原因
- 变更类型：`新增` / `修改` / `删除` / `拆分` / `合并` / `迁移`

### 附：第 53 项 omar 裁 a 并当日落地 — 编辑器补上「这次为什么改」

同日上午发现的图纸缺口当天收口。**omar 裁 a**：编辑器加一行修订说明输入（备选 b 是改口径承认 `notes` 只由 MCP / 导入写，否决——子决策 5 要的「再观测」是「改了什么、为什么改」并排，缺后半句切分点只剩一个日期）。

**改了什么**：编辑面正文框**下方**、三个坐标选择器**之上**，一行可选单行输入，label「这次为什么改」，写入 `alignment_phrases.notes`。四条契约——

1. **只在编辑态出现**，新建表单不渲染：新建没有上一版，没有可解释的修订
2. **正文未变时置灰**并给一行「改了正文才会记」。不藏起来，因为藏起来的字段等于没告诉用户可以留这一句，灰着的字段把条件一并说清楚了
3. **只填说明、正文没动 = 不算改动**：不进 dirty 判定，点外不保存、不进 discard 撤销流程。说明依附于一次修订，没有修订它就没有指代对象
4. **正文真变时总是写入，说明留空就是清掉上一条**；正文没变则整个字段不发、后端保留旧值。空也要写，是因为 `notes = COALESCE(?, notes)` 遇到省略会把**上一次修订的理由钉到这一次的切分点上**，指着新正文讲旧故事——这是 verifier 在首版实现里指出来的，改前留空等于沉默继承。覆盖上一条、不做历史（子决策 5 明写不建版本表），**打开编辑器时不预填旧说明**——预填等于把上一次的理由默认按到这一次头上

**一句话说清它现在只写不显**：明细面的「修订前 / 修订后」两段只带日期，说明只进导出与 MCP 读路径，**界面上没有任何地方回显**。展示待 [[HANDOFF]] 第 54 项；本次不动 `DriftLedgerView`。

**实现只动了三处**：`PhraseFormEditor` 的 `extraFields` 槽从 `ReactNode` 扩成「`ReactNode` 或一个吃 `{ contentDirty }` 的函数」（既有调用方零改动），`AlignmentPhraseEditor` 拿这个信号决定输入可不可写、并在提交时用**同一条谓词**决定发不发 `notes`，store 与容器透传这个可选参数。**Rust 与 IPC 一行未动**——写入方 P0 就在那儿了，缺的一直只是入口。

### 实施期发现

**verifier 抓出两个 P0 阻断，都是「测试全绿但语义错了」那一类**：

- **省略坐标载荷会把 `kind` 一起抹掉**——`update_alignment_phrase` 的坐标是可选载荷，而最初的实现把「载荷缺席」与「载荷是三个 null」当成同一件事，顺带把 `kind` 也重置了。后果是：**改一条中途口令的名称，会把它变回开场话术**，于是它从相位带上消失、也不再记 `live_cue`。修法是把两种情形彻底分开——缺席 = 一个字节都不碰，显式全 null 才清空；两条用例分别钉住这两半
- **只有 P0 时，口令复制会被记成 `phase_bar` 之类的入口**——`usage_records.source` 原本一律按「从哪个区点的」来填，而 `live_cue` 是全表唯一按**话术类别**而不是按入口记的取值。若照旧填入口，归因从第一天起就是错的，而且这张表 append-only、错账写进去就冻住了。修法是抽出 `alignmentUsageSource`，在四个复制点共用同一个判定

**P1 三处偏离，都是「契约没写、实现必须选一个」**：

- **「管理…」寄生在选择器的最后一个 `<option>` 里**——product-spec 只写了「入口在选择器内」。做成独立按钮会在 chip 编辑面里再加一个控件，与「零新按钮」的基调冲突；做成 `<option>` 的代价是它**不是一个取值却长得像取值**，选中后要立刻把选择器弹回原值再开管理面
- **废纸篓条数另起一句，不并进主句**——确认文案写成「影响 N 条话术。废纸篓里另有 M 条」，而不是「影响 N + M 条」。两个数的可核对性不同：前者用户翻得到，后者翻不到，合并会让一个查得了的数和一个查不了的数混成一个
- **`extraDirty`**——`PhraseFormEditor` 判「有没有改动」原本只看名称与正文，于是**只改坐标然后点外面，改动会被静默丢掉**。加一个 `extraDirty` 入参把坐标的脏位喂进同一套判定，而不是在外面另写一条保存路径

**P2 三处偏离**：

- **「停」没法单独成一行**——product-spec 区域 7 写「『停』单列一行」，但漂移账是按**锚点**聚合的，它不返回「哪条口令被复制了多少次」这一层。「停」因此与「口令自身在废纸篓」的那些复制一起，落在「**未归入任何一轴**」这一行里。契约要的语义（不进任何一轴）成立，要的版式（单独一行）没成立——**要单独成行，得让账多返回一层数据**
- **措辞禁令做成了正则扫描**——禁的词写成 `纠偏|漂移|出错|偏离|不好|建议|效果不佳|排名|评价` 一条正则，扫组件源码与渲染结果。它挡得住「有人手写了一句评价」，挡不住「换个词表达同样的评价」
- **明细那一格只认鼠标**（`tabIndex={-1}`）——状态栏按契约不进 Tab cycle（[[03-product-spec#13.4]] 六区），于是这一格进不了键盘可达路径。**这是照契约办的结果，不是疏漏**，但它意味着漂移账明细目前没有键盘入口

**一处契约层的观测，不是缺陷，路由给 omar**：状态栏那一格的范围是「本次唤起会话」（[[03-product-spec#13.3]] 区域 7），而 `wake` 会把计数清零；同时 `useCopy` 在**调用态**下复制完约 200ms 就隐藏窗口。两条都是已 ratified 的契约各自照做，叠起来的后果是——**这一格实际上只在整理态下读得到**：调用态里唤起 → 复制口令 → 窗口就没了，下次唤起计数又归零。改哪一条都是决策（放宽会话边界？调用态不隐藏？还是接受它就是整理态的读数？），所以这里只记不改。

### verifier 抓出三个缺陷，同批修掉

三个都不是「写错一行」，是**新机制自己长出来的**：

- **D1 `Unchanged` 分支不刷 mtime**——库没变时复用旧快照是对的，但不更新那份快照的 mtime，于是每日排期**永远结不清**：每小时的检查都算出「最近一份早于 24h」，每小时白跑一次 `VACUUM INTO`。哈希去重救下了磁盘，没救下 CPU
- **D2 导入改 async 后弹窗仍可关**——即上面第 4 条
- **D3 中断留下的 `.tmp` 残留不清**——快照先写临时文件再改名，中途失败就留下一个谁也不管的文件

三条各有一条回归用例守着，写在 [[07-features#3.16]] 的测试覆盖列里。

### 一脚踩在真实数据上，记明白

本轮跑 `bench:hotkey-wake` 时**没有隔离 `HOME`**，于是工作树里的二进制拿真实资产库跑了一遍，**把它从 `user_version` 12 迁到了 13**。`pre-migrate` 快照在，数据没丢，但这件事有两个后果要记：

### 为什么——第 32 项那个坑，是兜底自己把自己吃掉

旧实现的备份配额是**全目录共用五槽**。于是「迁移每次启动都失败」这个场景下，每次启动都拍一份新的 `pre-migrate`，五次之内就把所有旧快照挤光——**用户最需要兜底的时候，兜底刚好被自己挤没了**。

修法两条闸，缺一不可：

- **配额按前缀各自独立**——`pre-migrate` 的循环挤不掉 `daily`，反之亦然。这一条让不同来源的快照不再互相踩
- **哈希去重**——新快照与同前缀最近一份 sha256 相同则不落盘。这一条让「库根本没变」的重复启动不消耗配额

单开任何一条都不够：只做独立配额，五次失败照样挤光 `pre-migrate` 那五槽；只做去重，`daily` 仍能把 `pre-migrate` 挤掉。

#### G6-5 首轮两次没检出，值得单记

不是自检没生效，是**损坏没造成**。两个原因叠在一起：进程被 SIGTERM 结束不跑退出 checkpoint，WAL 里留着那些页的干净副本，而读页时 WAL 优先——刚写进主文件的垃圾被整个盖住；而且首次打的 page 2 是无关页，不参与 b-tree 校验。正确造法是先 `PRAGMA wal_checkpoint(TRUNCATE)` 清空 WAL，再打某张表的根页（`macros` 是 page 19）。

这与 §4.3 那条「走查记录里的根因，修之前再读一遍代码」是同一类错误：**看到「没报错」就写成「功能没生效」，而真相是输入根本没送到**。判一项验不过之前，先证明被测条件确实成立。

**四项据实记为未验**：`pre-import` 快照路径（既有能力，G5 前已验）/ 1 MiB 日志滚动是否真留一份旧文件（本门日志才 1618 B，离阈值三个数量级）/ 后台每小时线程跨长会话（本门靠拨 mtime 模拟时间，进程启了就退）/ 忙碌守卫。

这与本项目已经踩过两次的那类坑同形——公证 fail-open 与产物过期 fail-open，两次都是**步骤名叫着某个结果，而没有任何东西断言那个结果**（见 [[10-ops-spec#§7]] 7.3）。

### 为什么——把一个开环接成闭环，四步各有落点

现有工具在开场帮一下就结束了：话术复制出去，之后发生什么全靠人自己感觉。**这正是哲学四要消灭的那种「挥发掉的操作」**（[[01-spec#2.4]]）。ADR-029 把这条线接上，四步各对应一条子决策：

1. **感知**——中途出问题时用户本来就要复制一条口令换挡，那一下同时就是记账（子决策 3，`live_cue`）
2. **归因**——同一次唤起会话内，口令按轴归到它前面那条对齐话术头上计数（子决策 4，会话戳）
3. **修订**——改 `content`、把说明写进至今**从未有过写入方**的 `notes` 列、刷新 `content_revised_at`（子决策 5）
4. **再观测**——归因按那个时间戳切成前后两段，回答「改了之后是不是真的少漂了」（子决策 5 给切分点，子决策 4 给计数）

**四步里没有一步要用户额外按一个「这次出问题了」按钮。**显式按钮的信号更强、更无歧义，但哲学四的原始论断是：独立的沉淀动作，90% 不会被执行。选隐式的代价写在明处——**「复制口令 = 一次漂移」是一个未验证的假设**，本 ADR 建的是观测它的账，不是它的证明；若跑一段时间后噪音压过信号，再回来议显式按钮。

**显式不裁「8 相位是不是切错了」。**四轨与 8 相位是两套刀法：一维的 8 相位把「模式」与「产出契约」混在一条轴上，「挑错」在里面根本没有座位——本轮把它塞进「收敛」是将就，ADR 自己写明。但推翻一个已 ratified 且实装的模型，此刻只有一个原型的直觉可依，而那是本项目一贯拒绝的做法。**这条 ADR 建起来的账，正是将来判定要不要重切的唯一证据来源**——它把一个只能吵的问题，变成一个能等的问题。

## 2026-09-04（五）· 第一段 — 撤销 `verified` 判据的 ② ③ 条：状态表回答「验过没有」，不回答「够不够老」

> 触发：omar 2026-09-04 拍板——「这个规矩撤销吧，我自己执行就好了，没必要你去检查」。零代码改动，只改判据与随之失真的记账。

### 改了什么

[[07-features#§1]] 的 `verified` 原有三条判据：① 真机验收门通过或持续运行的自动化 gate，留证登记进 §7 ② 进入过一次已 publish 的 release ③ 自用 ≥1 周无回归。**② ③ 撤销**，`verified` 自此**只等于 ①**：证据存在，且登记在案。

发出去、用一阵子，这两件事照旧要做，只是由 omar 自己执行、自己判断，不再是一张 AI 维护的表里的阻塞条件。

### 为什么撤——它们不是「不可核」，是「不可作为」

2026-09-01 的 v1.19 修订解决的是另一个毛病：旧判据「E2E 通过 + 使用者 ≥1 周」当时**根本不可满足**（Playwright 未落地），判据成了摆设。那次修订的标准是「改成 AI 真能自己核的东西」。

**② ③ 通过了那次考试，却在另一个维度上不及格**——它们可核，但**不可作为**。一行留证已经完备的功能，唯一的前进方式是等日历翻页：没有任何人能做点什么让它动。状态因此从「验过没有」滑成了「够不够老」，而后者根本不是这张表存在的理由。

**「用了一周没出问题」这个信号本身不是废话**，它只是不该占状态表一格——它回到 omar 的判断里。**外部使用者位置不动**，仍是下一级门槛（[[HANDOFF]] 第 19 项）。

### 唯一动了状态的一行

[[07-features]] §3.8 **「删除可撤销」（ADR-028）`done` → `verified`**。它的留证 2026-09-03 当天就齐了——G5 八项全通过、零缺陷、零代码改动（[[11-test-spec#4.4]]），却因为 ② ③ 停在 `done`。它是这次撤销最直接的动机：**留证表第一次出现「证据齐了但状态不动」的行，补法只有等**。

矩阵 **70 verified / 7 done → 71 / 6**，合计仍 **92**。其余六行 `done` 逐行核过，缺的都是留证本身（四行「构造不出」：Modifier 种子数据 / SubStage 只有一列 / 剪贴板失败 / 断网；两行「拍不到、达不到」：800 ms 保存 toast / 需窄宽度的 footer wrap），与 ② ③ 无关，**一行都不动**。

### 连带销掉的失真

- **§4 节奏表 S1 行**写着「已发布自用但无一行 `verified`」——自 2026-09-02 v1.20 那 32 行升 `verified` 起就不成立了，§3.1 六模块早已 6/6。本次一并更正为 6/6 `verified` / §3.6 6/8 `verified`
- **§7 缺口表**末行整行离表（7 → **6**）。本表自此**只登记「缺留证」一种缺口**——那才是它管得着的东西。该行的**两处覆盖薄处不随之消失**（六个删除入口只真机走了 Macro 卡一处；祖先复活路径不经 WebKit 未真机跑），移入留证索引对应行与 §7 的 G5 段落，并在 [[HANDOFF]] 第 40 项留作低优先待办

## 2026-09-03（四）· 第六段 — **G5 真机门**：删除全链路在发布形态上跑完，八项全过；但状态一格没动

### 两处覆盖薄处，据实留着

1. **六个删除入口只真机走了 Macro 卡一处**。其余五处善后同走 `useUndoableDelete`，但触发器各由宿主自绘、措辞与焦点恢复各不相同，按 W3 的口径记推定通过
2. **祖先复活路径没在真机跑**（恢复一条话术连带复活它在废纸篓里的场景与子阶段）。它是单个事务里的纯 SQL，不经 WebKit——真机门存在的理由是抓 jsdom 看不见的那类失效，这条不属于那一类，由 `soft_delete_e2e.rs` 对应用例覆盖。**空白说清楚**：自动化能证「行回到了可见集合」，证不了「用户确实又在仪表盘上看见它了」

### 归档反查抓出 5 处

按 [[CLAUDE#§5.1.2]]，走查记录由只读子代理逐句反查代码后才写入，本轮 5 处不一致全部按代码改正：撤销 toast **不在 header 的 DOM 里**（是压在它上面的 `fixed` 浮层，「右上非底部」为真、「在 header 里」为假）/ 三图标动作簇**与整理模式无关**（无条件渲染，选整理态是走查纪律不是界面条件）/ 废纸篓说明行漏了一个由 JSX 换行折叠出来的空格 / 清空确认的 ✓ ✕ 另有 `aria-label` 且容器是 `role="alertdialog"` / 清空成功**除状态行外还发一条 toast**。另有一处措辞就地改准：**「（未知话术）」字面量并没有被删**，只是「有 `target_id` 却解析不到」的行不再可达。

### 方法记一笔

**合成点击对「悬停才出现的控件」太快了。** 一次自带 `mouseMoved` 紧接 `mouseDown` 的点击，React 还没渲染出动作簇，点击就落到下面那张裸卡片上——在调用态这等于一次复制加一次隐藏窗口，不是本来要点的删除。可靠序列是移动、等约一秒、截图确认簇已出现、再单独发一次点击。**更省事的那一半是选对模式**：卡级交互一律在整理态做，那里误点卡片本体既不复制也不隐藏窗口。这与 §4.3 教训 5 同源而不同面——那条讲「别误触发复制」，这条讲「等控件先出现」。**走查工具的时序假设也是被测对象的一部分**，这已经是同一族问题的第四次现身（前三次：拍不到浮层 / 收不到被占组合键 / 看不见别的进程持有的对话框）。

## 2026-09-03（四）· 第五段 — ADR-028 **P1 落地**：废纸篓有了界面；顺手堵上一个「恢复反而弄丢东西」的洞

> 触发：第四段 P0 落地后当日续做 P1。commit `6aca7eb`。P2 契约回流覆盖 P0 与 P1 两期，写在第四段末尾。

### 做了什么

- **设置 · 数据页新增废纸篓区块**：条目数（「N 项」）+ 每条一行（类型词 / 名称 / 删除时间，按删除时间倒序）+ 单条「恢复」+「清空废纸篓」。**条目数不是装饰**——子决策 4 用它换掉了自动过期，表会单调增长，用户得看得见它有多满
- **`ConfirmInline` 消费者由 0 恢复为 1**：清空走它，文案写明代价与数量——「彻底删除废纸篓中的 N 项，删除后无法恢复」/ 确认清空 / 取消。这是**应用里剩下的唯一确认框**，也是唯一还配得上确认框的动作
- **列表是组件本地状态、每次打开重读**，不进全局 store：另一个窗口可能在背后删除或清空，而一条废纸篓里的行按定义不属于 store 建模的那份「在用的东西」。另有一个 `useRef` 同步闩挡住连点——`busy` 驱动的 `disabled` 是状态更新，挡不住同一帧里的第二次点击，而 `purge_trash` 是真删，「至多一次」必须对得起竞态
- **读失败不退化成空列表**：读不到时显示错误，不显示「废纸篓是空的」——后者会告诉用户他的东西已经没了

### 顺手堵上的洞：单条恢复曾能造出一条谁也够不着的资产

**这是本段真正要紧的一件事，而 ADR 通篇没有设想过它。**

- **怎么发生的**：`SceneNotEmpty` 只数**存活**的子内容（这是子决策 7 与「废纸篓行不该挡住父行」的必然推论），所以**先删一条话术、再删它那个已经空了的场景，是允许的**。此后单独恢复那条话术：它的 `deleted_at` 变回 NULL，于是**废纸篓不再列出它**；而它的场景仍隐藏着，于是**仪表盘也渲染不出它**。行还在库里，用户既看不见也拿不回来
- **为什么这条特别刺眼**：**这正是本 ADR 存在的理由所要消灭的那种损失，却由本 ADR 自己的恢复路径制造出来。**一个安全网自己漏出来的洞，比它当初要补的那个更难被发现——因为用户会以为自己已经被保护着
- **修法是向上复活，不是拒绝恢复**：`restore_asset` 现在把被恢复行**挂靠的对象**一并复活——话术复活它的场景与子阶段，子阶段复活它的场景；另外五类挂在 `phases` 上或什么都不挂，而 `phases` 不是资产表、永远进不了废纸篓。**选向上复活的理由**：用户要的就是再看见这条资产，而不看见它所在的场景就看不见它；「父级还在废纸篓里就拒绝恢复」是把一个可以自动解决的问题推回给用户
- **连带效果**：`purge_trash` 里那条「跳过仍有存活子内容的废纸篓场景」的 FK 保护分支，**从可达降级为防御性**——现在制造不出那种状态了
- 子阶段那一步严格说不为可见性所必需（子决策 7 已让孤儿话术显示为未分组），仍然做，是为了让话术回到它**原来那一组**而不是悄悄换了分区

### 测试

前端 444→**457**（`TrashSection` 12 + `token-gate` 40→**41**——新增的 `TrashSection.module.css` 按 CSS 文件枚举自动入册，同一机制第二次现身，首次是 v0.3 的 `HotkeyRecorder.module.css`；`SettingsModal` 改了内容、条数不变）/ Rust 182→**183**（`soft_delete_e2e.rs` 6→7，新增的那条守恢复连带复活）。变异验证覆盖清空确认、恢复路径与父级复活。

### 知情留置两项（不是缺陷，已记 [[HANDOFF]]）

1. **StatusBar 的「今日复制」在清空废纸篓后到下次加载前会陈旧**——清空会删掉孤儿使用记录，而该计数不随之刷新
2. **恢复的成功 toast 可能被一条存活中的撤销 toast 顶掉**（Toast 让位规则的必然结果，[[05-design-spec#11]]），此时「那一行从废纸篓列表里消失」本身承担了反馈

两项都低优先：前者只影响一个统计数字且下次加载即正确，后者有替代反馈路径。

### 方法记一笔

**一个安全机制最危险的缺陷，往往是它自己新造的那个。** P0 建好了软删除，P1 建好了废纸篓，而「恢复」这个动作本身能把一条资产送进一个既不在废纸篓、又不在仪表盘上的夹缝——两个各自正确的规则（删非空场景只数存活子内容 / 恢复只改被点的那一行）叠在一起就漏了。**它没有被任何测试或闸门发现，是做 P1 界面时撞见的**：只有当废纸篓能被人看着，「恢复完它去哪了」才成为一个会被问出口的问题。这也是把 P1 排在 P2 之前的意外收益——**先让人看得见，再去写它应该是什么样。**

## 2026-09-03（四）· 第四段 — ADR-028 **P0 落地**：删除有后悔药了；六个确认框拆成一个撤销

> 触发：第三段 ADR-028 Accepted 后当日实施 P0。commit `77637cd`。**P1 见第五段**（同日稍后落地）；文档回流即 ADR 分期表里的 P2，两期合并成一批，记在第五段末尾。

### 做了什么

- **先修那两个坑，再动主体**（ADR §5「动手前必须先修的两个坑」）：① `idx_alignment_phrase_one_default_per_phase` 的谓词 `WHERE is_default = 1` **不认识隐藏行**，migration `0013` 重建为 `WHERE is_default = 1 AND deleted_at IS NULL`——不修的话，软删一条默认对齐话术后它仍占着那个相位的默认位，用户**永远设不了新默认**。全库另两处唯一索引（`sop_steps` 的 `UNIQUE (sop_id, order_index)` 与 `idx_drafts_hash_pending`）逐一复核，均不涉及本批的表 ② `toastStore` 的 arm 助手在一次 `set` 里覆写 message / action / seq，**任何后续 toast 都会在撤销窗口未过期时静默销毁撤销 toast**；改为带 action 的 toast 在存活期内不被无 action 的顶掉
- **数据面**：migration `0013_soft_delete`（`user_version` 12→**13**）给七张资产表加 `deleted_at TEXT NULL`。**不加索引**——每条列表读本来就全表扫（prd 的规模天花板是数百行量级），加索引只买到写入成本
- **写面**：七处 `DELETE FROM` 经新增的共享 `repo-write/src/soft_delete.rs` 改 UPDATE。**行不搬走**，所以 id / `created_at` / 分区 `order_index` / 指向它的每一条 `usage_records` 全部原样在位——这正是 ADR-022 与 ADR-025 两次否决「搬走再放回」时各自点名会丢的四样东西
- **读面 + 第七道闸门**：repo-core / repo-write / MCP 三个 crate 的读路径补 `deleted_at IS NULL`，并由新的 `src/ipc/soft-delete-gate.test.ts` **强制**——它读 Rust 源码，凡查资产表而漏写谓词即让 `pnpm test` 变红，豁免必须写注释并在清单里登记（当前 10 条四类：导出 7 / 废纸篓视图 1 / 删除路径存在性探针 1 / 恢复读取 1）。源码级 gate **6 → 7**
- **交互面**：六处「永久删除？」`ConfirmInline` 全部拆除，改**一键删除 + 撤销 toast**，善后收敛进新的 `src/hooks/useUndoableDelete.ts`（六处各有各的错误措辞与焦点恢复，但撤销失败怎么显示必须一致）。`ConfirmInline` **保留不删**，等 P1 的「清空废纸篓」——它将是应用里剩下的唯一确认框
- **销掉 G4 观察 O3**：最近使用区不再渲染「（未知话术）」墓碑。过滤放在 SQL 的 `LIMIT` **之上**——放到渲染层会让墓碑先占满名额再被抹掉，用户拿到一份莫名其妙变短的列表
- **测试**：Rust 169→**182**（含新 `soft_delete_e2e.rs` 6 条）/ 前端 414→**444**（含新 gate 12 条）。变异验证覆盖索引重建、恢复时的 `is_default` 降级、清空时的解绑、孤儿 usage 清理、toast 让位守卫、最近区过滤，以及六处删除中的两处

### 三处实装与 ADR 正文不一致，已在 ADR §2 逐条记明

- **重复删除是 no-op**：ADR 从未交代「删一条已经在废纸篓里的行」返回什么，实施时定为**成功的空操作**，照草稿软删的先例；撤销/重做竞态与双击都会走到这条路径，不该看到失败提示
- **导出 data schema 1.1 → 1.2**：ADR 子决策 6 只写了「`deleted_at` 一并写入导出文件」，**没料到那就是一次导出格式变更**。按 MAJOR 判兼容，所以 1.1 旧备份照常导入。这条兑现的正是 ADR §6「不可逆点」第 3 条自己的预警
- **最近区的过滤范围窄于子决策 5 的措辞**：只滤**带 `target_id` 却解析不到**的行；composition 的使用记录根本不带 `target_id`、永远解析不出名字，但**不在过滤范围内**——滤掉它们是产品行为变更而非 O3 修复。这条既有缺口 ADR 自己记为「同批可修」，**本次未修**

### 一处主动发现：既有留证过期了

[[07-features]] §7 留证索引里两行的 G4 证据（2026-09-02 拍的）**包含删除的两步确认形态**，而本批把它拆了。处理是**标注而不撤 `verified`**：删除的**能力**仍由当时的 SQL 反查证实（确实落库、删非空场景确实被拒），过期的只是「删除长什么样」那半边；撤掉会让「能力已验证」和「外观已改版」两件事一起丢失。重跑归留证缺口新行（**缺口 6 → 7**），等 P1 落地后一次走完删除 + 恢复 + 清空全链路。

### 方法记一笔

## 2026-09-03（四）· 第三段 — ADR-028 删除可撤销（原地软删除 + 第七道闸门 + 手动清空的废纸篓）

> 触发：omar 当日的第一性原理复盘——G4 走查剩下的观察项是「门把手」，不值得逐项清；真正的洞是**删除不可逆**，原话是「删掉一条话术，它就永远消失了」。这笔账在 [[06-prd]] §6.1、[[022-cross-scene-phrase-move]]、[[025-unified-anchored-editing]] 与 [[HANDOFF]] 第 13 / 21.2 项里挂了两个多月。

### 做了什么

- **两路调查 + 一路外部调研，得出三个决定性事实**（代码面 `del-surface` / 契约面 `del-contract`，均只读）：① **`deprecated` 隐藏管线已经建成、通着、有测试保护，但无人写入**——五张表带列、后端五处列表读已过滤、前端再过滤一次，缺的只是一个写入方 ② **全库没有任何级联删除**，migrations 里每条 FK 都是裸的而 `PRAGMA foreign_keys` 运行时为 ON，父行删除报错而非级联，**一次删除最多影响一到两行，不是一棵子树** ③ 本项目此前**两次否决**「把行搬走再放回」形态，理由都是同一组：会丢 id / 创建时间 / 分区排序位 / usage 历史
- **四个 Option 的取舍**：A 原地软删除（加 `deleted_at`，行不动）/ B 废纸篓表把行搬走 / C 不做软删除只靠 `VACUUM INTO` 备份快照 / D 复用现成的 `deprecated` 列当废纸篓。**选 A**——事实 ③ 直接判掉 B，而 B 换来的「读路径零改动」优势因事实 ① 在本项目里基本不存在；C 是整库回退到过去某一刻，删错一条话术要以丢掉此后全部改动为代价，**那是备份不是撤销**；D 成本最低但把「策展」（历史痕迹是资产的主动弃用）和「安全」（我根本没想删它）塞进同一个开关，且 `scenes` / `sub_stages` 本来就没这列、migration 一样省不掉
- **七条子决策**：① 新增 `deleted_at TEXT NULL` 与 `deprecated` 并列，读路径谓词变为 `deprecated = 0 AND deleted_at IS NULL`；用时间戳而非布尔，因为「何时删的」是用户判断要不要恢复的主要依据 ② **新增第七道源码级闸门**，断言凡查资产表必带这两个谓词，只豁免导出与废纸篓查询本身——**这条是选 A 的前提**，没有它 A 就退化成外部调研反复警告的那个坑 ③ 六处行内「永久删除？」确认框拆除改一键 + 撤销 toast，确认只留「清空废纸篓」一处 ④ 废纸篓**不自动过期**，不设保留天数也不设定时清理，只由用户在设置 · 数据页手动清空 ⑤ `usage_records` 一行都不动，资产恢复后历史自动重连（id 从未变过），最近使用区改为**滤掉解析不出目标的行**而不是渲染「（未知话术）」墓碑，顺带销掉 G4 观察 O3 ⑥ 导出保持全保真、包含废纸篓内容，因为一份丢掉废纸篓的备份会让「导出再导入」变成一次静默的永久删除 ⑦ 删除子阶段不再解绑其下话术，改为什么都不动，恢复因此是纯单行 UPDATE
- **依据**：拆确认框不是口味，是执行 [[025-unified-anchored-editing]] `:125` 已 ratified 的规矩「**撤销优于确认，但仅限真正可逆的动作**」——此前删除不可逆所以确认框是对的，本 ADR 让它可逆所以确认框该退场
- **动手前必须先修的两个坑**：① `idx_alignment_phrase_one_default_per_phase` 是 `WHERE is_default = 1` 的部分唯一索引，**不认识隐藏行**——软删一条默认对齐话术后它仍占着那个相位的默认位，用户将永远设不了新默认，migration `0013` 必须重建该索引 ② `toastStore` 的 arm 助手在一次 `set` 里覆写 message / action / seq，**任何后续 toast 都会在撤销窗口未过期时静默销毁撤销 toast**；撤销一旦成为主要安全网，这个缺陷必须先修

## 2026-09-03（四）· 第一段 — G4 观察 O7 裁决并修复：`AnchoredEditor` 接管锚点二次按下；product-spec v0.24

## 2026-09-02（三）· 第二段 — G4 缺陷 D1 修复：锚定编辑器首焦点改随定位

> 触发：HANDOFF 第 23 项（G4 缺陷 D1 · P1）。四个锚定编辑面（Macro / 对齐话术 / 话术 / 草稿）+ 场景属性面板打开后名称框没有焦点，键入落空，必须再点一次。v0.2.0 带着它发布。

### 做了什么

### ① 三枚 pill，删两枚留一枚

界面上原有三枚层标记文字标签。**它们看起来是一组对称装饰，其实其中一枚承重**：

### ② SOP 退出 Tab cycle：在屏 ≠ 值一个键盘停靠点

`SopProgress` 至今是单行占位（一个标题 + 一句「第三阶段实现」）。此前它既在屏、又占着区域级 Tab 的一站，于是**键盘用户每轮循环都要在那句占位文字上白停一次**。

裁决：**保留显示，退出 Tab**。区域级 Tab 由 **6 站降为 5 站**。

- 哲学二「同屏可见」只要求**在屏**——这一条继续满足
- 「值一个键盘停靠点」是**另一个**主张，今天不成立
- `data-region="sop-progress"` 保留，它仍是编号区域；真正的 SOP 导航器落地时 `tabIndex` 随它一起回来

顺带把 §13.3 区域 6 的长期账实不符**显式标注**了：正文描述的仪表卡是第三阶段目标形态，当前实现是单行占位。此前两者混在一起读不出区别。

|---|---|---|
| [[03-product-spec]] | v0.20 → **v0.21** | §13.3 区域 9 快捷键页：冲突由「一种形态」改写为**两种形态**，各自的界面交代写进契约 |

| [[11-test-spec]] | v0.4 → **v0.5** | 前端 395→**398**；**G3 项 2 由「不可达」重写为「通过」** |

### 两种冲突形态

1. **注册被拒**（竞态、系统保留但非 Carbon 持有的组合键）→ `register()` 失败 → 报「已被其他应用占用」+ 回滚旧绑定。**原本就有**
2. **按键根本没到**（更常见）→ 占用方在系统层截走，本应用既拿不到按键也拿不到错误 → 用户看到「按下去什么都没发生，而另一个应用跳了出来」。**本次补的是这一种**

### 判据为什么不是计时器

计时器会误伤犹豫的用户——盯着键盘想三秒就被告知「可能被占用」。改用**修饰键按下又抬起、期间没收到任何主键**：修饰键本身是普通按键会正常送达，被系统截走的只有主键，所以这个「影子」正是被吞掉那次按键的签名。提示出现后**保持录键态**，用户直接换一组即可。

### 门项不可达本身就是缺陷的症状

G3 项 2 上一段被判「不可达」，当时的结论是「门项写错了」。补完提示再看，更准确的说法是：**那个场景之所以观测不到，正因为产品在那里什么都不显示**。门项测不了和用户看不懂，是同一件事的两面。

### 复测时又踩了一次「怀疑复现手段」

第一次复测**提示没出现**，差点结论成「修复无效」。实为走查工具不忠实——`key.swift` 只在主键上打修饰键标志位，**从不发送修饰键自身的按下/抬起事件**，而判据恰好依赖那对事件。人手按 `⌥Space` 会发，合成的不会。改用 `chord.swift`（先发修饰键 keydown → 主键 → 反序抬起）后一次复现成功。**这是第三段「拍不到 ≠ 不存在」的同一条教训换了个面孔：没复现要先怀疑复现手段。**

### 验证

前端 **398/39 文件**、eslint / tsc / prettier / `pnpm build` 全绿。真机复测：第二个实例占住 `⌥Space` → 第一个实例录键态按 `⌥Space` → **提示按预期出现**、录键态保持、绑定仍为 `Control+Shift+KeyP`、旧组合键事后正常。走查跑在隔离 `HOME` 上，**真实资产库未触碰**（已核对绑定值未变）；⚠️ 但界面偏好不受 `HOME` 隔离，见下。

### 撤销一条自报的疑点：「首装是浅色」不成立

走查时用隔离 `HOME` 起实例，界面是浅色、设置里「浅色」为选中态，一度记为「首装可能拿不到 [[024-dark-cockpit-identity]] 的深色身份」。挖出那份存档：`{"themeMode":"light","accent":"blue","density":"compact"}` —— **是 omar 自己的旧开发版偏好，不是首装默认值**，疑点撤销。

根因值得记档：**`HOME` 覆盖只隔离数据库，隔离不了界面偏好**。SQLite 确实落到了临时目录，但 WebKit 的 localStorage 不认 `HOME` 覆盖，照旧读写真实的 `~/Library/WebKit/prompt-hub/...`。于是「空白配置」这一半根本不空白。

⚠️ **连带更正一句说过头的话**：第四段原写走查「全程隔离 `HOME`，真实资产库未触碰」——**资产库确实没碰（已核对绑定值未变）**，但界面偏好被写到了真实存储里。半隔离不该被描述成隔离。

单选项、可逆、不改 ADR-027 任何已批子决策——按 [[CLAUDE#§5]] §5.3 不构成「二选一的不可逆决策」。裁决与证据记在 [[027-configurable-global-hotkey]] §2。

### 三条子决策

1. **绑定存 SQLite `settings` 表，不是 localStorage**。理由只有一条且是硬的：快捷键在 Tauri `setup()` 里注册，那一刻 webview 还不存在。localStorage 方案只能「先注册默认键、前端挂载后再改」，而**改键的用户恰恰就是默认键冲突的那批人**——等于每次启动必然先错误注册一次。`open_and_migrate` 本就排在 `register()` 之前，SQLite 方案时序上零改造
2. **冲突探测只有 `register()` 失败一种形态**（macOS 无 API 枚举占用者）。改绑走「校验 → 注销旧 → 注册新 → 落库」，**顺序是决策不是实现细节**：先注册成功再落库，保证「库里的值 == 当前真正生效的值」；任一步失败回滚旧绑定。硬约束：强制至少一个修饰键——裸键全局快捷键会在所有应用里吞掉该键，而唯一的撤销途径正是这个键本该唤起的窗口
3. **新增 macOS `RunEvent::Reopen` 逃生口**，防「配置把自己锁在门外」。**顺带修掉一个独立缺陷**：窗口 `visible: false`，此前点 Dock 图标毫无反应

### 起草时更正了 HANDOFF 自己的两处记载

- **「破 `settingsStore.ts:18` 的界」不成立**：该注释主语是 *appearance prefs*，唤起键是行为绑定不是外观偏好，**边界从一开始就没盖住它**。真正要新写的是一条可机械执行的归属判据（**何时被读**，而非重要程度）
- **`settingsStore.globalHotkey` 是死字段**：有默认值、有 setter、不在 `partialize` 白名单、全仓零消费者，而两条测试正钉着一个没有读者的机制。副产品：它的默认值 `"Alt+Space"` 恰好就是插件的 accelerator 格式，格式选型无需重拍

### 实施期两处口径修订（写进 ADR §2，不改原文）

1. **缺行回落默认值，不再 `fail_startup`**：原文写「读不到 = 库损坏」，与子决策 3 的第三层逃生口（`sqlite3` 手改 `settings`）自相矛盾——手改时打成 `DELETE` 会让应用**永久开不了机**，把逃生口变成砖头
2. **`set_global_hotkey` 必须是 `async` 命令**：插件的 `register()` 内部 `run_main_thread!` 派发并阻塞等结果，而同步 IPC 命令本身就跑在主线程上 —— 同步版本首次调用即主线程自锁死

### 顺带修掉的两处 P1-a 既存缺陷

均非新决策，是 P1-a 容器本身的洞，迁移到更高的面板时才暴露：

- **超高面板的 footer 出界**：只夹取**原点**不够。高于 dashboard frame 的面板被钉在顶部内缩处，footer（保存 / 取消）跑出画面下沿——**正是 ADR-025 触发事件 A 的缺陷在另一块面板上原样复现**。`useAnchoredPosition` 增报 frame 相对的 `maxHeight`，面板内部滚动。该值不能写进 CSS：外壳是 inset 浮动框而不是视口

## 2026-08-19（三）· 第四段 — P1-a 交叉审查：规则表四处未落地 + 接口契约提前到 P1-a

### 变更内容

两个独立 agent 对上一段（P1-a）做交叉审查，各自命中同一批缺陷。**四条 CRITICAL 不是新决策，是 [[025-unified-anchored-editing]] 子决策 2 的规则表写了但代码没实现**，直接修，未开新 ADR：

- **撤销回来的草稿点外即静默丢弃**（`PhraseFormEditor.tsx`）：dirty 原以「字段种子值」为基准，而撤销 toast 恢复的草稿是**带种子回填**的，于是 `canSave=true` + `dirty=false`，规则表「未改动→直接关闭不发 IPC」分支抢在保存前面。用户按文档说的「点外 = 保存」点出去，既没落库也没提示。修法：新增必填 `mode: "create" | "edit"`，dirty 改以**已落库值**为基准——创建态基准恒为空，无论字段被什么种子填过
- **「拒绝关闭」状态下点另一条铅笔仍丢草稿**（`Editor.tsx`）：`editingId` 是单槽，pointerdown 拒绝关闭后，**同一次按压**的 click 照样落到另一条的铅笔上、改写单槽、卸载刚才拒绝关闭的面板。修法：`onDismiss` 返回 `false` 表示拒绝，`AnchoredEditor` 捕获相位吞掉该次按压的 click——「不关闭」必须意味着这次按压什么都不做（对应 omar 裁决「拒绝期间锁住，不允许切到另一条」）
- **「取消」按钮完全绕过规则表**（`PhraseFormEditor.tsx`）：原 `onClick={onClose}` 直连。同一份脏草稿按 `Esc` 有撤销 toast，点「取消」直接销毁。两个都是放弃入口，现统一走 `handleAbandon`
- **点外触发的保存失败全静音**（`AlignmentPhrases.tsx`）：`handleCreate` / `handleUpdate` 不 catch，`handleSave` 又吞异常。同文件的 delete / move / set-default 全都走 `showError`，只有保存这条没接。点外保存发生在用户视线已经移开之后，静默失败与成功**逐像素相同**。现补 `showError` + 重抛（`onSubmit` 契约写明调用方必须提示后重抛）

**接口契约从 P1-b 提前到本段**（ADR §6 原定「迁移前先定接口契约」，omar 裁决提前堵）：

- `AnchoredEditor` 删 `open` prop——**挂载即打开**。焦点归还写在卸载 teardown 里，`open={false}` 保持挂载会静默吞掉焦点归还

## 2026-08-16 — 最近使用去重下沉到 SQL（了结 2026-08-10 的已知取舍）

### 变更内容

- **`list_recent_usage` 在 LIMIT 之前按资产去重**（`repo-core/src/repo.rs`）：加 `ROW_NUMBER() OVER (PARTITION BY target_type, target_id IS NULL, COALESCE(target_id, id) ORDER BY timestamp DESC, id DESC)` + `WHERE rn = 1`，`limit` 从此计的是**不同资产**而非原始行。连拷同一 Macro 40 次不再挤掉其余资产（2026-08-10 记为「已知取舍：单资产刷满取数窗口时 wake 会欠填」的那条，现已消除）
- **NULL 语义是这次的坑**：HANDOFF 原方案写的 `GROUP BY target_type, target_id` 会把所有 `target_id IS NULL` 的行归成一组——composition 用法本就不带 target_id，会被折叠成一条。分区键补 `target_id IS NULL` 判别位，既复刻客户端旧语义，也杜绝真实 target_id 与兜底 record id 撞车
- **客户端去重整条删除**（`prompt/helpers.ts`）：`dedupeRecent` + `RECENT_FETCH_LIMIT` 移除，两处调用点（`loadSlice` / `recordingSlice`）改为直接取 `RECENT_LIMIT`(5) 行并原样渲染。**保留冗余过滤会在 SQL 回归时静默兜底**，与本项目连栽四次的 fail-open 同形，故选单一真相源
- **测试口径迁移** 前端 345 → 335 / Rust 155 → 158：删去 10 条 `dedupeRecent` 单元用例（行为已不在前端），Rust 侧补三条——重复折叠且 LIMIT 计不同资产 / 无 target_id 行不合并 / 跨表同 id 不合并；promptStore 集成块由「recent wake dedupe」改为「recent wake fetch」，改钉两件事：只要 `RECENT_LIMIT` 行、返回什么就渲染什么（重新引入客户端过滤会让它变红）
- **注释订正**：`commands.rs` 的 `RECENT_USAGE_LIMIT_MAX` 说明仍写着「渲染端取 40 行窗口再客户端折叠」，已同步；`repo.rs` 新注释按 `count_today_usage` 既有口径写明全表扫描代价（< 10k 行可接受），并显式禁止「给内层扫描加边界」这种把病灶推远的改法

### 变更原因

2026-08-10 引入客户端去重时即在特征测试里钉了结构解法（SQL 侧去重）。本轮兑现，同时消灭跨语言的双重去重语义。

### 变更原因

第一阶段 MVP 实施后发现 design-spec v0.6 token-only 没给「质感锚点 / 组合规则 / 组件 pattern / 状态规范 / icon / 视觉权重」，AI 实施时按字面拼 token 出工程师审美 UI。ADR-012 锁 Linear-class 整体气质后，需要把质感锚点固化成**外部 AI 工具（Claude Design 等）能接受的接口契约**——这是「L5 协作契约层」。

该层与 L0–L4 性质不同：派生自上游而非自源、bump 触发包括"外部 AI 工具能力升级"。详见方法论 v1.3 §5.15-16。
